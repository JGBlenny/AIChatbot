## 2. 目標形態（業界做法，原文渲染存於 `~/jgb-archive/arch-step3-20261018/industry-dates/`）

- **由解析器把口語轉成正規化值。**
  - Amazon Lex：「Converts words that represent dates into a date format. The date is provided to your intent in ISO-8601 date format.」（`lex_date.txt`）
  - Dialogflow CX：`@sys.date` 的輸出格式是 `{"year","month","day"}`；zh-TW 的 `@sys.date-period` 範例把「四月」轉成 `startDate 4/1～endDate 4/30`（`dfcx_sys.txt`）。
- **缺年份時的推定方向**
  - Dialogflow CX 只在缺元素時推定，方向由設計者決定。原文：「If there is ambiguity in end-user input due to missing date/time elements, the nearest matching future date/time is returned together with 3 additional nested date/time fields (past, future, partial)」「To ensure a past date is returned, you can use parameter preset…」
  - Lex 的文件只寫了不帶年份的例子（「November twenty-fifth」），原文是「This defaults to dates on or after the current date.」。帶年份時怎麼處理，文件沒寫（未查完）。
- **在 LLM 架構下，由模型填值、程式依值的規則檢查。**
  - Rasa CALM：「You can use the from_llm slot mapping type to fill slots with values generated by LLM-based command generators.」（`rasa_slots.txt`）
  - Rasa CALM 的 `rejections`：「the if property is a condition … evaluated using the pypred library」「When validation fails, your assistant will automatically try to collect the information again.」（`rasa_steps.txt`）
  - 這裡的檢查對象是值，不是原話字面。
- **限制**：以上只查了 Lex、Dialogflow CX、Rasa 三家，以及 Microsoft Recognizers-Text 與 Duckling 兩套解析庫。這不是全業界的做法。

## 3. 差距（現況，附可 grep 的符號）

1. `services/agent/bill_period.py` `parse_period`：年份只認 `_YEAR_MONTH_RE`（`YYYY-MM`／`YYYY/MM`）。「2027年1月」只命中 `_ARABIC_MONTH_RE`，再由 `_year_for_bare_month` 推成最近的過去，結果是 2026-01。
2. `services/agent/write_forms.py` `BILL_DUE_EXTEND_FORM` 的 `FormField("period", …, "text")`，走 `runtime.py` `_write_draft_gate_value` 的 text 規則（必須是原話子字串）。模型正規化成「2027/05」就被丟掉，期別遺失，`tools/confirm.py` `_resolve_bill_by_period` 只能依物件列候選。
3. 同一個檢查函式裡，`date` 型別已經是「解析值 ∈ 原話解析集合」的做法（`parse_model_date` 對 `user_text_dates`），只有期別還停在字面比對。

## 4. 路徑（單片）

### 4.1 改動

| 項目 | 改什麼 | 服務規則 |
|---|---|---|
| P-1 | `parse_period`：新增「YYYY年M月」與「YYYY年＋中文數字月」（年、月之間允許空白），和 `YYYY-MM` 同屬「有年份」；有年份時不呼叫 `_year_for_bare_month`，也不被 `YEAR_MODIFIER_TERMS` 覆寫。判定順序維持固定：有年份的寫法 → 阿拉伯數字月 → 中文月 → 這期 → 上期。 | R1、R2 |

### 4.2 不做

### 4.3 偏離目標形態的取捨

- 業界把正規化值交給流程用。我們進一步規定存「程式從原話解析的值」而不是模型值，讓存進去的值在構造上就來自使用者。這比業界做法更嚴，理由是寫入路徑的防捏造要求（DSP-085、DSP-091）。
- 解析器沿用自家的 `parse_period`，不換 Recognizers-Text：它的 Python 套件在官方頁標示為「(alpha)」，而且「這期／上期／未繳」是我們這個領域特有的寫法。這是判斷，不是業界依據。

## 5. 安全審查結論（`security-reviewer`，核可前，2026-10-19）

審查總結：擬議值閘**沒有開出新的捏造出口**。原因是存進草稿的值一定是程式從原話解析出的項目；而且在「去年九月→模型只給九月」「相對期別跨月漂移」兩種情況下，比現行的 text 子字串規則更嚴。弱點不在值閘本身，而在原話集合 U 的正確性取決於解析器。逐條處置如下：

### 5.1 依審查補的設計

- **P-1b**：新增 `parse_periods(text, today)`，回傳一則原話裡**所有**期別（每個月份、這期、上期各算一項）。年份修飾詞只綁緊鄰在後面的那個月份，例如「去年九月」。值閘的 U＝每則原話 `parse_periods` 的聯集，也就是使用者講過的期別全部算數，由模型從中挑一個。下游 `parse_period` 只會讀到存進草稿的正規化字串，語意除了 P-1 與 P-1c 之外維持不變。
- **P-1c**（依業主 Q-ROC 裁示「維持現行」：只有西元年才算「有寫年份」）
  - 「四位數年份＋年＋的＋月份」（例如「2027年的1月」）視為有年份，照 R1 解析。
  - 「四個中文數字（〇、零、一～九）＋年＋（空白或「的」）＋月份」（例如「二〇二七年一月」「二零二七年 一月」）是 P-1c 唯一回「解析不到」的情形：`parse_period` 整句回 None；`parse_periods` 只丟掉這一項，同一則原話的其他項照收。
  - 一到三位數的年份（民國年「115年9月」「116年1月」、「27年1月」）維持現行行為：只吃月份、往回推。
  - 「年」後面沒有緊接月份的句子（年資、租期，例如「我租了2年，九月的延三天」「我租了2年 九月的延三天」「租約一年」）不觸發，行為和現在相同。
  - 四位數西元年的解析照 P-1、R1，年、月之間允許空白（「2027 年 5 月」）。
- **「明年」「前年」「後年」**：`parse_period` 維持現行行為（整句回 `None`）。`parse_periods` 只丟掉緊接在它後面的那個月份項。
- **P-2 未繳規則（固定）**：比對只看年月。存值格式為 `YYYY/MM`，只有在**模型值與使用者原話都含未繳詞**時才加上「 未繳」。模型只給「未繳」、而且原話裡有未繳詞時，存「未繳」；否則拒收。存值必須完全符合 `^\d{4}/\d{2}( 未繳)?$|^未繳$`。

## 8. 已裁示的問題

**Q-ROC：民國年（例如「115年9月」）怎麼處理？** 2026-10-19 業主選「維持現行」，選項原文：「只有西元年才算「有寫年份」，民國年照舊只吃月份、往回推。講到跨年（例如「116年1月」）仍會推錯。」以下保留當時的問題內容，供日後查證：

現行行為：「年」前面不是阿拉伯數字月，所以只吃到「9月」，再由往回推推成 2026/09。當年、當月的民國年講法碰巧是對的，跨年的講法（例如「116年1月」）就會錯。

可選做法：

- **(a) 回「解析不到」**：之後只能依物件列候選。當年的民國年講法會比現行退步。
- **(b) 只有西元 YYYY 才算「有寫年份」**：民國年維持現行行為，跨年的講法照舊推錯。
- **(c) 換算民國年**：「三位數 100～199＋年」加 1911。兩位數或中文數字的年份仍走 P-1c，回「解析不到」。

主會話建議 (c)。台灣使用者常講民國年，換算規則封閉、可完整驗證，所以 (c) 對使用者的結果最好。不過它超出原話 1「YYYY年M月」的字面，須經業主裁示。

已依裁示落實：R2 旁記錄裁示；C1 的正對照加入「115年9月」⇒ 2026/09、「116年1月」⇒ 2026/01，兩者都要和改前相同；非目標寫明跨年民國年仍會推錯。
