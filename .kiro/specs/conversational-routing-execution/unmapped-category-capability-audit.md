# 未 mapping category 的 capability disposition 盤查

- 日期：2026-08-29｜方法：純 SQL。代表例以**固定規則**選（同 category 內 `id` 升冪取首／中／末；
  ≤3 筆則全列），⛔ 未人工挑「最能證明問題」的標題。
- 目的：**先判斷 category 有沒有能力承擔 nomination evidence 這個角色**，
  ⛔ 不是問「要不要補 mapping」——後者會重新掉進「category = responsibility」的舊坑。

⚠️ 數字更正：先前寫 53 個未 mapping category，那次查詢未排除 `對話規則`／`系統脈絡`。
以情境知識為母體的正確數字是 **49 個**。

## 最重要的發現：**六個 `條件診斷：*` 分類全部沒有 Face**

對照：`條件診斷：帳單` **有** mapping（→ `bill_diagnosis`）。

⇒ 這不是我看 category 名字判的——**KB 自己的命名慣例**就把這些標成診斷情境，
而它們的標題全是「為什麼我這個 X 不能／沒有／失敗」，非查個別狀態無法回答。
**七個診斷類只有一個被接上。**

## 三個結論

```text
① GENERAL_ONLY 占大宗 ⇒ 「78.4% 無 mapping」看起來嚇人，但多數不是問題
② 真正的結構缺口很具體：**六個 條件診斷：* 分類（21 筆）零 mapping**，
   而第七個（帳單）有 —— 同一套命名慣例只接了七分之一
③ MIXED 才是最深的一層：合約管理 43 筆、帳單管理 26 筆同時承載制度與實值查詢
   ⇒ 問題可能不是「漏補 mapping」，而是
     **category 這個粒度不足以表達 responsibility applicability**——
     這直接支持裁定 001（category = nomination evidence ≠ responsibility authority），
     並進一步指向：**連作為 nomination evidence，它可能都太粗。**
```

## 本盤查**不能**回答

```text
⛔ production 有多少 request 被漏接
⛔ 某 category 應該以多少比例進 Face
⇒ 兩者都需要真實 Layer-0 traffic
```
