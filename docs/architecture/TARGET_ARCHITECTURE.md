# 對話服務架構（目標）

**最後更新：2026-10-31**

> 本檔回答一個問題：**這個系統應該長什麼樣。** 架構的目標只寫在本檔。
> 現況看 [`SYSTEM_ARCHITECTURE.md`](./SYSTEM_ARCHITECTURE.md)（全景）與 [`AGENTIC_MCP_ARCHITECTURE.md`](./AGENTIC_MCP_ARCHITECTURE.md)（一回合的流程）；現況文件寫的是目前跑的樣子，不是設計依據。
> 新功能、計畫、改動都以本檔為準：現行工作就是對齊這份架構（DSP-130、DSP-131）。要改分工，先改 DSP-091 並經業主核可。

📐 邊界規則見 `docs/architecture/BOUNDARY.md`。

## 0. 一句話

**本系統是對話服務，不是 MCP 系統。呼叫端走專用對話 API 進來；AI 負責聽懂使用者，有業務規則、有後果的環節由程式掌握；JGB 工具由 JGB 維護，本系統當 MCP client 呼叫。**

三件容易讀錯的事：

1. `/mcp` 不是最終的對話入口。它是現況，呼叫端改完就關。
2. JGB 工具現在放在本系統內只是暫時的，一定要搬出去。
3. 換入口與搬工具都不改分工。AI 只提出工具呼叫，由 AgentRuntime 執行；AI 不打 JGB API。

---

## 1. 使用者成功的樣子

1. 問知識題得到只依核可知識的答案；不足時被告知缺什麼、被追問，而不是被捏造或直接丟給真人。
2. 辦事（報修、延期、建物件／合約／帳單）時，說過的不被重問；說錯可以改、可以取消、中途插問別的再回來；按確認後真的完成，沒完成時被誠實告知。
3. 系統說出口的「請確認」「已完成」「已轉真人」永遠等於實際狀態。
4. 問完說謝謝就收尾，不被轉真人；真的需要真人時被清楚轉過去。
5. 接入方拿到結構化內容自行呈現，不必解析文字。

## 2. 分工：誰決定下一步

**AI 負責聽懂使用者，並在知識作答與一般對話中自己決定怎麼查、怎麼答；凡是有業務規則、說錯或做錯會造成後果的環節，下一步由程式依宣告與狀態決定**（DSP-091）。

| 環節 | 誰決定下一步 | 說明 |
|---|---|---|
| 理解使用者這句話要什麼（意圖、欄位值、要更正、要取消、要真人、已解決） | AI | 以標籤輸出，⛔ 讓 AI 填代碼 |
| 寫入全程：缺哪欄、出不出卡、能不能送出、送出後回什麼 | 程式 | |
| 已選定的那筆紀錄（候選列出、使用者選了哪一筆、後續都用這筆） | 程式 | |
| 帶狀態的句子（請確認、已完成、已取消、已轉人）與確認卡、按鈕 | 程式 | AI 只組不帶狀態的話 |
| 轉人規則（含收尾）：何時轉、先問還是直接轉、道謝即收尾 | 程式（規則） | AI 只提供「使用者要真人／已解決」的理解 |
| 知識完全查無時的出口（「處理不了」） | 程式 | AI 組話 |
| 知識作答：要不要查、查哪段、怎麼組答案；只答得出一部分時說明缺什麼、部分回答、追問 | AI | 只依核可知識（DSP-066）；答案有沒有依據由 Verifier（程式）把關 |
| 一般對話、追問的措辭 | AI | |
| 唯讀查詢（帳單、合約等）：依 AI 理解出的查詢條件，由程式查詢並篩選 | 程式 | AI 自呼工具只在程式接不住時用：該類查詢程式尚未宣告，或程式讀不出查詢條件；程式已宣告的查詢類型 AI ⛔ 繞過 |

**兩個方向都算違反**：

- ⛔ 任何計畫或改動讓 AI 決定上表「程式」列的下一步。
- ⛔ 程式重新理解使用者的話：自己解析原話得出值或意圖，用它取代或否決 AI 的理解。程式只驗 AI 結果的格式、範圍、值域，並決定下一步（DSP-127）。

## 3. 原則（計畫引用這裡的編號）

| 原則 | 內容 |
|---|---|
| **P0** | **混合式：理解交給 AI；有規則、有後果的環節由程式掌握**（環節分工見 §2）；程式 ⛔ 重新理解使用者的話；P1～P8 為其展開 |
| P1 | 寫入全程（建立→確認→更正→送出／取消→收據）由程式持有；動作差異只在動作宣告 |
| P2 | 說出口的狀態（請確認、已完成、已取消、已轉人）只由程式依實際狀態產生 |
| P3 | 給模型的資料與給人看的呈現分開 |
| P4 | 在程式掌握的環節，理解層輸出結構化指令（寫入意圖、更正、取消、選擇、要真人、已解決），下一步由程式決定；知識作答與一般對話不經指令層 |
| P5 | 對話修補（更正、取消、中斷回原流程、澄清、候選選擇、處理不了）是共用模式，所有程式掌握的流程共享 |
| P6 | 知識題只依核可知識作答；不足時說明＋部分回答＋追問；查無走「處理不了」 |
| P7 | 轉人與收尾由規則決定：明確要求直接轉、卡住先詢問且不連發、道謝即收尾 |
| P8 | 本系統出結構化內容（卡、按鈕、狀態）＋文字備援；外觀由接入方決定 |

## 4. 目標架構圖

```
呼叫端（一般程式，不是 AI）
  │ 對話 API：HTTP；取上傳票也走這裡。附件直傳對話服務
━━ 對話服務（本系統）━━
對話入口
  │ 驗金鑰、身分、額度；讀寫會話狀態；照片與文件前處理；收檔
AgentRuntime（對話核心）
  │ 程式：機器值、草稿、閘門、確認卡、轉人、回話
  │ AI：理解使用者、知識作答、一般對話的措辭
  │ 大綱與系統自有工具（函式呼叫）：kb.*、help.read、session.slots.*、handoff.request
  │ confirm.request：確認卡與 token 是本系統的；要查 JGB 的部分經 JGB 工具代理
  │ JGB 工具代理：本機工具清單、寫入確認檢查、解碼與投影、依據標記
  │ 四條對外的線：
  │   ① 模型呼叫（HTTP，Chat Completions）→ 模型服務
  │   ② 查詢 embedding（HTTP）→ embedding 服務（進模型的回合挑細目；失敗時模型只拿到目錄）
  │   ③ 文件與照片辨識（HTTP，傳檔）→ DocuMind（謄本、收據、修繕照片；只辨識）
  │   ④ 呼叫 JGB 工具：方向是 MCP 協定，對話服務當 MCP client；移交片實測後確認
━━ 工具服務（JGB 維護，不在本系統）━━
JGB MCP server
  │ 查帳單、查合約、建修繕單等；回結構化原始資料
JGB API
```

## 5. 目標架構的邊界

- 呼叫端只走對話 API，不碰 MCP；取上傳票也走對話 API。
- 模型呼叫、embedding 與辨識都不走 MCP；只有呼叫 JGB 工具走 MCP。修繕單照片的位元組以 HTTP multipart 送 JGB（§6），也不走 MCP。
- 只有外部 AI 要把本系統當工具呼叫時，才另開 MCP 入口。這是選配，不是對話入口。
- AI 提出工具呼叫，AgentRuntime 執行；唯讀查詢與寫入的下一步由本系統程式決定；寫入要已兌現的確認 token 才能發出，JGB 不必知道已確認。
- **工具清單由本機決定**：給模型的工具來自本機白名單，⛔ 用 `tools/list` 動態餵模型。寫入工具只由本機代理註冊，一律過確認檢查。JGB 工具定義和本機登記不一致就封鎖該工具。
- **工具結果語意留本機**：JGB 回結構化原始資料並訂輸出 schema；解碼、投影、依據標記、查無與沒查成的分離，都留在 JGB 工具代理。
- **身分由程式每次注入**：不放工具參數，模型看不到。新入口要處理 `Identity.entry` 與命名空間身分。
- **寫入工具搬過去的前提是 JGB 支援冪等**：JGB 現在沒有冪等機制，MCP 2026-07-28 版又要求串流中斷時重送。
- **帶事實的句子要過 Verifier 才能送出**：對話 API 可以串流狀態與不帶事實的句子；帶事實的句子要逐字串流，得先做逐句 Verifier。換入口不會自動得到逐字串流。
- JGB 工具一定要搬出去。連線用 MCP 或 JGB 維護的 REST 客戶端，是 JGB 工具移交片要實測決定的做法，不影響搬出去這個目標；MCP 連線的延遲未實測。

## 6. 修繕單附照片（API 規格 #22，DSP-136）

照片走 API 規格 #22：客人按確認後，由程式把欄位與照片一次以 `multipart/form-data` 送到 JGB 的 `POST /api/external/v1/repairs`（照片在 `broken_photos[]`）。照片本體不走 MCP，也不進模型。

```
對話服務                                          JGB
  │ HTTP multipart：修繕單欄位＋照片位元組＋冪等鍵 ──▶ POST /api/external/v1/repairs
  │ ◀─ 建立結果（data.id）
```

- 照片位元組只取自確認卡綁定的暫存；送出前重算 sha256，對不上確認卡就不送，⛔ 退回成不附照片照送。
- 確認前 JGB 不收任何檔案。
- JGB 端規則（staging `544e8592eb`）：≤10 張、每張 ≤5,000,000 bytes、JPEG／PNG，檔案與網址不得同時給；同一冪等鍵重送不重複掛。
- JGB 工具移交片若要改走 B（JGB MCP server 申請上傳、HTTP 傳檔、MCP 建單）或 E（multipart 上傳換 `file_id`、建單帶檔案編號），要附推翻卡由業主裁（DSP-136）。

## 7. 四條路

| 路 | AI 做什麼 | 程式做什麼 | 工具由誰發起 |
|---|---|---|---|
| 知識作答 | 決定要不要查、查什麼、怎麼組答案 | Verifier 把關答案依據；完全查無的出口 | AI 提出 `kb.*`、`help.read`，AgentRuntime 執行 |
| 唯讀查詢 | 理解要查什麼、什麼條件 | 依 AI 理解的條件查詢、篩選；已宣告的查詢類型 AI ⛔ 繞過 | 程式；AI 自呼只在尚未宣告或讀不出條件時用 |
| 寫入 | 理解動作與欄位值 | 驗值的格式、範圍、值域；草稿、追問、查紀錄、帶狀態句與確認卡文字、出卡；客人按鈕後兌現 | 程式（`confirm.request`、`jgb2.action.*`） |
| 按鈕與清單點選 | 不參與（機器值回合） | 全部 | 程式 |

## 8. 現況與目標的差距

| 項目 | 現況 | 目標 |
|---|---|---|
| 對話入口 | 專用對話 API `POST /api/v1/agent/turn`（對外 `{AICHATBOT_BASE}/v1/agent/turn`，DSP-134）與 `POST /mcp` 並存，正式機尚未部署新入口；現有呼叫端仍走 `/mcp`；沒有逐字串流 | 呼叫端只走對話 API，`/mcp` 關閉 |
| MCP 門面 | 仍是工具入口兼過渡對話入口，本系統是 MCP server；兩入口共用的入口核心 `_make_invoke` 在 `mcp_facade.py` | 對話入口搬出去；本系統不必當 MCP server |
| 上傳票 | 對話 API `POST /api/v1/agent/upload-ticket` 與 MCP 門面的 `agent.upload_ticket` 都發 | 只由對話 API 發 |
| JGB 工具 | `jgb2.*` 與 `JGBSystemAPI` 在本系統內，函式呼叫 | JGB 維護，本系統當 MCP client 呼叫；語意層留本機 |
| 寫入確認檢查 | `_wrap_write_tool` 在工具層 | 拆到本機 JGB 工具代理 |
| 唯讀查詢 | 由主模型自呼工具 | 程式依 AI 理解的條件查詢、篩選 |
| 知識完全查無 | 沒有程式先發的出口 | 程式出口 |
| 程式重讀原話 | 部分環節由程式重讀欄位值原話 | 程式只驗 AI 結果的格式、範圍、值域 |
| 修繕單照片 | 正式機接真 JGB 時不附照片；本系統的 #22 改接（開關 `JGB_WRITE_WIRING`，只在連 staging 時生效）已寫好、正式機尚未部署 | 照片以 multipart 送 JGB（§6，DSP-136） |
| 繞過工具層的呼叫 | AgentRuntime 直呼 `confirm.py`、`write_candidates.py`、`write_forms.py` 與 `services.jgb` 的函式，並直接 import `tools/jgb2.py` 的語意函式；`confirm.request` 本體與它的下游查 JGB；MCP 門面的 `_open_repairs`、`_repair_category_tree` 閉包與 `action_tools._resolve_category` 未經 `registry.call` | 全部經 JGB 工具代理 |
| 測試底座 | 模擬客人與回測走 `agent.turn`；`JGBMockTransport` 替代 JGB | 改前改後走同一入口；工具搬走要有 MCP 替身 |

## 9. 怎麼走到目標

- **對話入口**：排在切換正式機之前（主會話讀法）。已用加法新增專用對話 API（契約與取捨見 DSP-134），與 `/mcp` 共用同一個 `_invoke`；`/mcp` 留到呼叫端改完才關，入口核心搬出 `mcp_facade.py` 也等那時一起做。
- **JGB 工具**：JGB 要先建 MCP server，本系統不能單獨完成；排序看 JGB 能否配合。
- 分片、順序、驗收方式與進度不寫在本檔：見 `.kiro/specs/agentic-mcp-orchestration/architecture-target-20261018.md` §4 與 `HANDOFF-20261018.md`。
