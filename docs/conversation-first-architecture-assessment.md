# 對話優先架構評估：檢索問答骨架是否仍合適

> 版本：v1（2026-07-10）
> 評估問題:系統以「檢索中心單輪問答」起家,重心已遷移到對話流程(面向診斷/售前顧問/表單互動/LINE),原骨架是否仍合適?若不合適,終態長什麼樣、怎麼走過去?
> 前置文件:docs/chat-architecture-overview.md(實然全貌)、docs/line-bot-integration-plan.md
> **狀態:候選 C(混合骨架)已由使用者拍板(2026-07-10)。遷移路徑 P0-P3 為執行基準。**

## 1. 結論先行

**骨架重心不合適了,但不是推翻,是推廣一次已經發生的反轉。**

- 底層資產(檢索/formatter/API/lookup/configs/面向配置)全部保留,從「管線主幹」降為「引擎工具箱」——反轉的本錢。
- prospect 已完成 engine-first 反轉並生產驗證(對話擁有回合、知識降為 grounding)——目標形狀的活樣本。
- 建議終態是**混合骨架(候選 C)**而非全反轉:對話脈絡與交易/診斷意圖由引擎擁有回合,冷啟動的單輪資訊問答保留檢索快路徑(快取+低成本,現行 85.4% 品質資產)。
- 遷移分四階段(§6),LINE Phase 1 不需等反轉,LINE 自由問答升級與反轉第二階段對齊。

## 2. 現狀骨架與重心遷移的證據

**現狀**:一則訊息=一次檢索仲裁=一個答案/動作。對話以三種「例外」形式存在:
1. Step 0 攔截(進行中會話,對話偽會話借住 form_sessions,需佔位 schema 解 FK)
2. Step 1.5 特例(prospect engine-first,硬開的分支)
3. 檢索側門(b2c 診斷面向要「命中≥0.75+分類掛診斷配置的知識」才進得了對話)

**重心已遷移的證據**:五個診斷面向收案(合約/帳務/帳號/物件/IoT)、售前=純對話、prospect 演化三步(無知識分支→engine-first→知識降 grounding,使用者拍板)、LINE 主打租客對話場景、回測框架已被判定「單輪評估與多輪面向不相容」——連測試體系都在說重心變了。

**兩台多輪機器互不能調用**(對碼確認):面向引擎無法觸發表單→「對話式報修」(聊著聊著收齊欄位)做不到,只能「命中→切換逐欄位模式」。

## 3. 三個候選終態

| | A 維持現狀 | B 全反轉 engine-first | C 混合骨架(建議) |
|---|---|---|---|
| 回合擁有者 | 檢索(預設)+攔截特例 | 引擎(所有角色所有訊息) | 規則制:①進行中對話→引擎 ②交易/診斷意圖→引擎 ③冷資訊問答→檢索快路徑 |
| 每輪成本 | 檢索+1 LLM 優化;快取可 0 LLM | +1 Brain 調用/輪;快取失效(對話有狀態) | ③保留快取;①②接受 Brain 成本 |
| 延遲 | 現行 | 每輪多一跳 LLM | ③不變;①②多一跳 |
| 品質可控 | 檢索分數可觀測、回測基準在 | Brain 判斷黑盒化;85.4%/80% 基準全失效需重建 | ③基準沿用;①②需多輪評估(回測現代化本來就欠) |
| 對話體驗 | 二等公民,特例持續增生 | 一等公民 | ①②一等公民 |
| 工作量 | 0(但每加一個面向多一個特例) | 大爆炸,回歸範圍=全部 | 分階段,每階段獨立驗收 |
| 風險 | 架構債複利:特例間衝突、觸發語彙續碎 | 一次賭注太大 | 邊界規則本身要維護(意圖路由) |

**A 的真實成本**是隱性的:面向每加一個、LINE 每上一個場景,都在往「例外」堆——Step 0 的讀取順序陷阱(已有陷阱5)、觸發語彙碎片化(P0 債)都是這個複利的表現。
**B 否決理由**:租客流量大宗仍是單輪資訊問答(客服電話/操作/規定),檢索+快取是這類的最優解;為了對話場景把 FAQ 也塞進 Brain,是把便宜問題變貴、把可測問題變黑盒。
**C 的本質**:承認系統服務兩種負載——「查一下」和「辦一件事/搞懂一件事」——各給最優骨架,邊界由明確規則而非攔截順序決定。

| SOP | 與知識並行比分的第二語義層 | **帶退役時程的過渡層**（§4.5 評估定案 2026-07-11）:P2 前維持仲裁覆蓋共存;P2 意圖規則上線＝門檻優勢消失＝遷移窗口,整層退役、仲裁段隨之刪除,客製終態載體=業者知識＋lookup＋引擎業者配置 |
| 表單 | 獨立狀態機,檢索觸發後接管 | 引擎可調用的執行策略之一(逐欄位=固定槽位序列);獨立入口保留(按鈕 trigger_form_id) |

| 對話面向 | 檢索側門進場的診斷模式 | 引擎的領域模組(進場改走意圖規則,不再賭 0.75) |
| lookup/API/configs | 動作分派的資料層 | 不變(引擎工具箱) |
| 快取 | 檢索路徑的加速器 | ③專屬(①②有狀態不可快取,本來也沒快取) |
| 觸發語彙(trigger_mode 等) | 碎片化+半失效(P0) | ③修斷鏈續用;①②大半退役(Brain 取代關鍵詞確認)——**修 P0 時只修斷鏈,死欄位直接清,不要投資 auto 機制** |
| 離題偵測 | 表單專屬(trigger_intents) | 引擎 scope-switch 已內建同能力,收斂後退役 |
| 計量/額度 | middleware per-message | 不變(架構無關) |

### 4.5 SOP 存廢評估（2026-07-11 定案：可取代，退役掛 P2）

**功能對照（P0 修通知識層觸發後）**：SOP 零獨佔能力——manual/immediate 確認流知識層等價（借同一 sop_trigger_handler，e2e 已證）、immediate_prompt 等價、業者維度等價（vendor_ids）、資料型答案 lookup 更適、多步引導引擎更強；SOP 獨有的 followup_prompt／next_api_config **實查使用皆 0 筆**。唯一實質差異＝**觸發門檻**（SOP 0.55 vs 知識 0.6 勝出＋0.75 觸發表單）。

**內容結構（404 條 active 實查）**：資訊型 none＝231（→業者知識/lookup）、交易型 form_fill＝167（→知識錨點）、api_call＝6（→知識 api_call）。

**定案**：lookup＋對話引擎＋知識層**功能上可完全取代 SOP**；不即刻取代的唯一理由是門檻不對稱（遷移即觸發率下降）。**P2 意圖規則上線＝門檻優勢消失＝遷移窗口**：404 列腳本化搬遷（含 embedding 重生）＋admin 兩個 SOP 管理頁工作流調整＋仲裁段（chat.py:1815-2104）刪除（管線簡化）。P2 前新建業者客製一律優先走業者知識/lookup，SOP 只留存量不增量。

**業者客製的取代配方**：規定/政策→業者知識列；資料→lookup/configs；觸發客製（先確認/開場詞）→業者知識錨點＋trigger_mode/immediate_prompt（P0 修通、e2e 已證）；互動流程→表單＋chaining/決策樹（觸發＝業者知識錨點）；對話式 persona→引擎配置。

**參數化階梯（「每業者都有類似規定」≠每業者建一次）**：①差異只是值→一筆通用知識＋`{{參數}}`占位（vendor_parameter_resolver 生產中，vendor_configs 填值）②有/沒有→通用知識＋模組開關 ③流程結構→通用表單基準＋真不同者建變體 ④政策實質不同→才建業者知識列（僅不同者建，餘 fallback 通用）。新業者上架成本曲線＝填表（參數/開關/lookup 匯入）非建置；checklist 需同時管「填了」與「真值」（vendor 3 佔位假值前例）。設計項①僅第④級涉及。

**P2 遷移前置設計項（三件，2026-07-11 查證）**：①**業者知識優先規則**——知識層內部無「業者列必勝通用列」機制（排序純比相似度，priority 僅同分決勝，vendor_knowledge_retriever_v2.py:119-121）——SOP Case 3.1 的等價物需設計（同分類業者加權或檢索後同題去重業者優先）②**引擎配置加 vendor 維度**（現僅 per target_user）③**表單變體解鎖**（UNIQUE(form_id)→複合鍵，解析層已備）。

## 5. 風險與未知數據(先定標準再執行)

**判準(退場條件,執行前定死)**:
1. 品質:③路徑沿用 85.4% 基準不得退步;①②需先建多輪評估基準(回測現代化為前置,已立案候選)
2. 成本:①②每輪成本上限=現行 direct_answer 成本×N(N 待定,依 usage_events 實測現行分佈)
3. 延遲:①②p95 不得高於現行面向對話(prospect 已是此形狀,有現成基線)

**待收集數據**(2026-07-10 實查 usage_events:僅 42 筆 7/7 冒煙流量,計量剛上線,無真實租客流量——租客端未開放,分佈數據上線前不可能存在):
- 租客流量的「查一下 vs 辦事/診斷」分佈:**改為上線後驗證項**——C 的流量假設(FAQ 為大宗)以假設身分成立,租客端開放後 30 天用 processing_path 分佈重驗,若對話負載占比遠高於預期則 P2 提速
- 每輪成本基線(冒煙數據,n=42,方向性參考):conversational 路徑 avg 2.0 次 LLM/輪、$0.0065/輪、8.5s,vs 非對話路徑 1.1 次、$0.0052、3.9s——**引擎回合≈2.2× 延遲、+27% 成本**,此即 §5 判準 2/3 的初始基線
- 0.6–0.75 灰帶占比:**任何表都沒存檢索分數**,需埋點(usage_events 加 retrieval_score 欄或側表)——併入 P0 一起做,成本極低、對 P2 的意圖路由設計是關鍵輸入

**主要風險**:
- 意圖路由邊界(②的判定)做壞=把 A 的攔截順序問題換成路由規則問題——規則必須少而明確(交易動作封閉集合+診斷分類),不搞機率性
- 表單機收斂進引擎是最大工程(狀態機語義遷移),放最後、獨立立案
- b2c engine-first 之前,租客視角補全案(§9 已知缺口)必須先收,否則引擎巧婦難為

## 6.5 維度模型（骨架 × 維度，2026-07-11 補）

C 骨架只是脊椎；完整架構＝骨架 × 四個正交維度。**原則：維度參數化骨架、不分叉骨架**——每維度只在指定層位生效，不產生第二條管線（現系統既有紀律：b2b/b2c 同一 API、隔離靠欄位不靠分支）。

| 維度 | 生效層位 | 終態運作 |
|---|---|---|
| 通路（Web／LINE） | 入口層 | 身份取得（jgb2 session／LINE 綁定表）＋渲染；chat API 之下不感知通路 |
| 角色（mode×target_user：租客/房東/業者員工/prospect/internal） | 回合歸屬規則＋能力邊界＋引擎 persona | 每角色一組配置：知識池、個資能力（雙證）、對話規則（DB 驅動 per target_user）、回合歸屬預設（prospect 已反轉、租客 P2、業者員工待議） |
| 業者（vendor） | 工具箱層 | 隔離（vendor_ids/SOP/lookup/configs/計量額度）＋客製四層（參數→知識→SOP→表單變體）＋就緒度（開關/資料已匯/SOP 建置，上架 checklist 統一） |
| 業態（business_types） | 知識可見度過濾 | 與角色獨立維度（既定裁決），決定知識對業者前台的可見性 |

**角色終態表**（2026-07-11 對碼補齊；業者員工歸屬經查證**已收斂，非開放題**——b2b 跳 SOP 但知識分類路由無 mode 驗證，診斷面向今天就以 b2b＋property_manager＋真 role_id 生產運行，五面向 e2e 皆此身份收案）：

| 角色 | 終態回合歸屬 | 現況 | 缺口與案子 |
|---|---|---|---|
| prospect | 引擎全對話 | ✅ engine-first 生產中 | 無 |
| 業者員工（b2b） | 混合：診斷→引擎／FAQ→快路徑 | ✅ **已是此形狀**（面向經分類路由進引擎） | 進場仍走 0.75 側門（P2 一併改意圖規則）；表單/交易不開放（業者用 JGB 後台操作，非缺口） |
| 租客（b2c） | 混合：診斷/交易→引擎（含調表單）／FAQ→快路徑 | 機制就緒、視角參數未建、入口未開放 | 租客視角補全＋P1 引擎調表單＋P2 進場規則 |
| 房東 | 混合（同租客） | 未建置（純 DB 可加，已驗證） | 隨租客案帶入 |
| internal | 計量排除 | ✅ 在跑 | 無 |

**P2 風險修正**：b2c 反轉不是全新賭注——是把 b2b 已生產驗證的混合形狀複製到租客側（＋引擎調表單能力），骨架先例又多一個。

**其餘維度缺口**：①通路—LINE 綁定與 per-vendor rich menu（LINE plan）②業者—就緒度統一管理（差距 #8）。

## 7. 對 LINE 案的含義

- **不等反轉**:LINE Phase 1 的修繕流程(按鈕→表單→建單→查詢)用現行機制完全夠,gateway 只碰入口層,反轉發生在語義層以下、對 gateway 透明。
- **反轉反而被 LINE 加速**:LINE 租客的自由輸入天然是對話負載(①②),P2 的第一個受益者就是 LINE;「對話式報修」(P1 POC)是 LINE 體驗的殺手級升級——傳一張照片+一句「冷氣壞了」直接聊完建單。
- Gateway 設計不需為反轉預留任何東西(介面是同一個 chat API)。
