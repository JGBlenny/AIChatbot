## Phase 0 — 準備（動任何東西前的安全檢查）

### 0-1 確認起點
```bash
git rev-parse --short HEAD
```
- **做什麼**：印出 prod 現在在哪個 commit。
- **為什麼**：整套計畫假設 prod 停在 `6607031`。**若不是 6607031**＝這期間有人動過 prod，範圍就變了——**先停，別往下跑**。

### 0-2 備份線上資料庫（最重要的保險）
```bash
mkdir -p backups
docker exec aichatbot-postgres pg_dump -U aichatbot -d aichatbot_admin | gzip > backups/pre_deploy_$(date +%Y%m%d_%H%M).sql.gz
ls -lh backups/pre_deploy_*.sql.gz | tail -1
```
- **做什麼**：把整個線上資料庫 dump、壓縮、存成帶時間戳的檔；最後列出剛存的檔。
- **為什麼**：後面會改資料庫（跑 migration、砍欄位）。萬一整庫級災難，這是唯一救得回來的東西。
- **一定要看**：檔案大小要**幾十 MB** 才正常；0 或幾 KB＝dump 失敗，**別繼續**。
- **還原（萬一）**：`gunzip -c backups/pre_deploy_<時間戳>.sql.gz | docker exec -i aichatbot-postgres psql -U aichatbot -d aichatbot_admin`

### 0-3 確認安全開關
```bash
grep RAG_API_AUTH_ENFORCE .env
```
- **做什麼**：檢查 prod 認證開關。
- **為什麼**：沒開的話任何人能帶任意 role_id 直打 API、繞過權限。**應顯示已開**；沒開先設定再部署。

## Phase 4 — 真跑（SQL＋seed 一次做完、自動記帳）
```bash
export DB_HOST=localhost DB_PORT=5432 DB_PASSWORD=<prod資料庫密碼>
export EMBEDDING_API_URL=http://localhost:5001/api/v1/embeddings
bash rag-orchestrator/database/migrate.sh --apply
```
- **做什麼**：真的執行 Phase 3 列出的那些——逐支跑 SQL＋跑 seed，每支成功即自動記帳。
- **為什麼帶 export**：seed 批要連 DB＋呼叫 embedding 服務產生向量，故先設密碼與網址（`<prod資料庫密碼>` 換真的；埠位以 prod 實際為準）。
- **出錯怎麼辦**：runner 出錯即停、失敗的不記帳。看訊息**修那一步 → 再跑一次**（冪等，已成功的自動跳過）。

## Phase 6 — 煙囪＋空白驗證（runbook §5）
```bash
# 認證已開 → 驗證 curl 要帶金鑰（從 .env 讀 §16 發行的那把）
K=$(grep '^RAG_ADMIN_API_KEY=' .env | cut -d= -f2-)
curl -s -o /dev/null -w "HTTP=%{http_code}\n" -X POST http://localhost:8100/api/v1/message \
```

- **做什麼**：帶金鑰打一題「查無」的問題看狀態碼；再數 log 裡還有沒有那個 NameError。

- **為什麼**：這正是這次修的空白 500 bug。**預期 `HTTP=200`、NameError 計數＝0**。
- **接著**：跑 runbook §5 的 20 面向煙囪，確認核心功能沒被弄壞。

## 貫穿全程的原則
- **fix-forward**：任一步失敗 → 修那一步 → 重跑（migration 冪等），不倒退。
- **本次範圍**：解掉空白 500（NameError → 前端空白氣泡）。
- **不在本次**：查無時 `{{service_hotline}}` 生變數未代換——屬另一個 issue（資料/文案層），另案處理。
