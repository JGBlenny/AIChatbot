## 一、要驗證的假說（唯一）

> 既有 Conversational Brain 已具 routability 判斷能力，但判斷發生在 commit **之後**。
> **把既有判斷提前到 commit 之前，能否降低錯誤面向進場，而不大量犧牲正確進場？**

**不是**「新增一顆 routing selector」。B 階段不新造判斷模型。

---

## ⛔ 方法更正（2026-08-23，執行後回填）

**「241 筆回歸」作廢。** 兩個理由：

1. **邏輯上是錯的集合**：pre-entry gate 只在「進面向」那條路徑生效，
   不進面向的案例**程式路徑根本不會走到**——跑它們是在量必然不變的東西。
2. **直接跑 OFF/ON 各一次會被上游污染**：14 案實測即發生——
   兩筆「被 gate 擋」的案例在 OFF 臂本來就沒進面向，差異來自檢索變異而非 gate，**無法歸因**。

**改用的方法**（實際執行）：

```
72 筆歷史 routing queries（僅作母體）
  → 用當前系統、Gate OFF 跑一次，記錄系統自己提出的面向
  → 凍結 routing proposals (query, proposed_face)
  → 只對這批凍結 proposal 做 gate replay（上游完全固定）
```

分母也隨之更正：**不是 72，是「目前仍會提出面向 routing」的那批**。

## 二、兩層基準，角色不同，**不得混用**

| 基準 | 筆數 | 角色 | 為什麼能用 |
|---|---|---|---|
| `test_scenarios` b2b 未污染集 | **241** | **回歸／副作用偵測** | 未被本輪 prompt 調校污染；用途是抓大面積行為改變，**不需要標註** |
| 針對性 replay 集 | **14** | **針對性診斷** | 有人工標註（6 錯路由＋8 正確路由）；用途是確認已知 routing failure 是否被修復 |

⚠️ **14 案不得作為最終成績。** 它是診斷集，樣本小且刻意挑過。

### 241 筆為何不需標註——用「差異」而非「絕對正確率」

重新標註 241 筆成本高且不可靠（本輪已有 72 筆標註因 runner 失真而作廢）。
故 241 筆的驗收採**基線快照 → 差異比對**：

1. **B0 先跑一次全量，凍結為基線快照**（每案記：是否進面向、進哪個、最終答案、來源知識）
2. B1/B2/B3 各跑一次，與基線 **diff**
3. 只有**行為改變的案例**才需要人工看——這把標註量從 241 降到數十

## 三、五項指標（實作前凍結）

| # | 指標 | 定義 | 量在哪 |
|---|---|---|---|
| 1 | **Routing precision** | 實際進面向的案例中，進對面向的比例 | 14 案（有標註）|
| 2 | **False accept** | 不該進面向卻進了 | 14 案 |
| 3 | **False reject** | 應進面向卻被擋掉 | 14 案 |
| 4 | **Direct fallback correctness** | **被擋掉之後，回到直答／查無是否安全** | 241 差異案例，人工看 |
| 5 | **Workflow coverage** | 有多少原本可完成的 API／多輪任務因此進不去 | 241 差異案例，人工看 |

### ⚠️ 指標 4、5 是本契約的重點

**「判對不要進這個面向」不等於整題答對。** 例如：

```
我想增加一個物件
  → 擋掉 contract_create_guide  ✅ routing 正確
  → 但接著被直答成錯誤 KB        ❌ 整題仍然失敗
```

**這不算成功。** 任何只報指標 1–3 的結論視為不完整。

## 四、通過線

### 14 案（針對性）
基線：錯路由 6（brain 可攔 3、穩定漏放 3）／正確路由 8（誤殺 0–1）

- **必要**：把 3 個穩定 `stay` **再攔下一部分**（≥1），且正確路由誤殺 **≤2/8**
- **不設「6/6 全攔」**——其中「帳單發送按鈕按不了 →`billing_flow`」連我自己都標為可議

### 241 案（回歸）
- **行為改變的案例逐一檢視**，其中「原本進面向 → 現在直答」者，
  指標 4、5 不得出現**系統性劣化**（定義：改變案例中劣化多於改善）
- 未進面向的案例行為**應完全不變**（gate 只在進場前生效）

## 五、實驗必須拆成四組，不得一次全改

| 組 | 內容 | 要回答 |
|---|---|---|
| **B0** | 現況 | 基線快照 |

### 邊界（不得逾越）
- **不動全域 validator**。`llm_answer_optimizer` 的 `action` 驗證維持現狀。
  entry path 做窄修，mid-session 行為完全不碰。
- mid-session switch bug **另開 ticket**，不搭便車。
- 以 feature flag 控制，可一鍵回復。

## 六、結論分兩級，不得越級宣稱

| 級別 | 條件 | 可以聲稱 |
|---|---|---|
| **一級** | 241 ＋ 14 通過 | **技術上可行、regression-safe** |
| **二級** | 未來新的 production holdout 通過 | **routing 品質確實提升**，可決定正式 rollout |

⚠️ **一級通過不得對外聲稱「routing 品質提升」。**
現有兩個基準都不是 production holdout：
241 筆來歷未確證（`created_by=backtest_user`），14 案是刻意挑的診斷集。

### 為何不等 production 資料才動工
B 不是新架構，是**把已在線上執行的判斷提前**，且 entry-scoped ＋ feature flag ＋
不碰 mid-session。風險受控，可先用 241 做工程驗證。
S3 回報自 2026-07-29 起零新增，等它會讓一個明確且可控的修正被外部資料供給卡死。

## 七、B 階段執行結果（2026-08-23）

### Cohort 重建：72 → 67 仍會路由

用當前系統（Gate OFF、b2b 已停用 query rewrite）重跑 72 筆歷史 routing queries：

| | 筆數 |
|---|---|
| 仍會提出面向 routing | **67** |
| 已不再進面向 | 5（**4×R4 ＋ 1×R5**）|
| 提出的面向與歷史不同 | **0** |

⭐ 提出的面向 **100% 與歷史相同**——先前離線 facet 分析在「哪個面向」上是對的，
錯的只是周邊數字。

### Gate replay（上游凍結，每案 3 次多數決）

| 標註 | 仍會路由 | 被擋 | 率 |
|---|---|---|---|
| R1 正確（錨點）| 9 | 1 | 11%（誤殺）|
| R2 正確（一般 KB）| 39 | 0 | 0% |
| **R3 方向對、證據錯** | **11** | **0** | **0%** |
| **R4 明確錯路由** | **2** | **1** | **50%** |
| R5 可議 | 6 | 0 | 0% |

- **錯路由攔截率 1/13（7%）**
- **正確路由誤殺率 1/48（2%）**

### ⭐ 結論：不建議上線。理由是作用面，不是有害

**1. R3 全數漏放，而且是結構性的。**
11 筆 R3 同一形狀（「物件下架後還能再上架嗎？」→`estate_guide`、
「作廢發票的按鈕為什麼卡住了？」→`billing_invoice`）。
**brain 判 stay 是對的**——這些問題 topic 上確實屬於該面向。
錯的是「觸發它的那篇知識答不了這題」。
**R3 是 answerability 的病，不是 routability 的病，gate 結構上治不了。**

**2. R4 已自行縮小八成。**
R4 從歷史 6 筆掉到現在 2 筆——4 筆因其他改動（多半是 b2b 停用 query rewrite）
已不再進面向。gate 在剩下 2 筆中攔了 1 筆。
**這個改動想修的問題，在它建好之前就自己縮小了。**

**3. 投入產出不成比例**：13 筆錯路由攔 1 筆，唯一攔得動的類別只剩 2 個案例。

### 處置
- 程式**保留在分支**，`PREENTRY_ROUTABILITY_GATE` 預設 `false`，fail-open。
- 等 R4 型錯路由在**乾淨語料**上重新顯著時再評估。
- **真正的大宗是 R3（11 筆）**——但那要的是「進面向後，觸發知識答不答得了這題」
  的判定，屬 answerability 軸，**不是本 gate 的射程**。

### 契約自評
本契約要求的五項指標中，①②③ 已量；
**④ direct fallback correctness 與 ⑤ workflow coverage 未量**——
因結論已是「不上線」，未再投入。若日後重啟本案，這兩項仍為必要項。
