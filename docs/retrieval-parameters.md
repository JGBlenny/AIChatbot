# 檢索與對話路由｜參數台帳

> 建立 2026-08-22（分支 `fix/retrieval-routing-stability`）
> 依據：[檢索召回盤查與適用性把關](./retrieval-recall-audit-20260822.md)
> 用途：每個可調參數的**現值、控制什麼、動它會怎樣、有沒有實證**。
> 鐵則：**沒有實證欄位的參數不要動。** 本輪三次因「離線與線上不一致」翻盤，
> 任何調整都必須以驅動真實 API 的方式驗證。

## 一、本輪已改（分支內）

| 參數 | 舊值 | 新值 | 為什麼 |
|---|---|---|---|
| `QUERY_REWRITE_MODEL` | `gpt-3.5-turbo`（顯式設定＋程式 fallback）| **跟隨 `OPENAI_MODEL`**（現為 `gpt-4o-mini`）| 3.5-turbo 產出簡體與中國用語（租戶／请求／规定），改寫後向量偏離知識庫用詞 |
| `QUERY_REWRITE_TEMPERATURE` | `0.3` | **`0`** | 改寫是檢索最前端，隨機性被下游放大；實測同句 5 次有 2 次路由到錯面向 |
| `RELEVANCE_GATE_MODEL` | 未設 → fallback 寫死 `gpt-3.5-turbo` | **跟隨 `OPENAI_MODEL`** | 同一 prompt 換模型差 12 分（8/25 → 20/25） |
| `RELEVANCE_GATE_SKIP_VEC` | `0.85`（向量高於此免判）| **未設＝不跳過** | 高語意相似正是本閘門要擋的型態，拿它當免判理由自相矛盾 |
| `SCORE_SHIFT_PROBE` | 空字串會拋錯 | **空字串視為未設定** | compose 展開為空字串 → 每次檢索 500。見 commit `d5c9848` |

## 二、待決參數（需要拍板或更多實證）

### `FORM_TRIGGER_THRESHOLD` = `0.75` ⚠️ 影響最大

**一顆門檻同時管兩件事**：面向進場 **與** 表單觸發（`services/decision_layer.py`
`facet_entry_eligible` / `form_trigger_eligible`）。

| 面向 | 說明 |
|---|---|
| 控制什麼 | top-1 知識 final ≥ 此值，且其 `categories` 命中啟用面向 → **進多輪對話，繞過適用性把關** |
| 實測影響面 | 約 **30%** 的 b2b 流量被面向截走 |
| 已知問題 | 0.75 實測**零攔截**（所有截流案例都遠高於它），明顯過鬆 |
| 往上抬的效果 | ⚠️ **低信心**：曲線是對 17 個錯誤案例擬合，樣本來歷未確證、單人標記一次。可用結論僅「0.75 過鬆」，**具體數字不要從該樣本挑** |
| 為何門檻不是解法 | 6 筆資訊型問題以 final **≥0.945** 進面向——任何門檻都擋不到。需要的是 routability 判定 |
| 風險 | 抬高會同時影響**表單觸發**（同一顆值），須分開評估 |

**建議**：先確認是否要把面向與表單的門檻**拆成兩個變數**，再談數值。

### `KB_SIMILARITY_THRESHOLD` = `0.65`
知識進入答題候選的門檻。本輪未量測，**不要動**。

### `RERANKER_MIN_VECTOR_SIMILARITY` = `0.3`
送進 reranker 前先砍掉向量低於此值的候選（`base_retriever`）。
實測日誌常見「下限 vector>=0.3 砍 0 筆」——目前幾乎不生效，**不要動**。

### `RERANKER_INPUT_LIMIT` = `20`
送進 reranker 的候選上限。⚠️ **注意交互作用**：query rewrite 會把候選從 20 擴到
30–43 筆，這個上限會再砍回 20——**擴充來的候選有一部分直接被丟棄**。
本輪未量測被丟棄的是不是有價值的，**值得單獨查**。

### `ADVISOR_TEMP` = `0.4`（程式預設，env 未設）
最終答案生成的溫度。**任何 e2e 對話實驗會被它污染**——
本輪實測同句 5 次答案措辭皆不同（路由相同）。
做 e2e 量測前應暫時設 0，或接受措辭變異。

### `ENABLE_QUERY_REWRITE` = `true`
⚠️ **改寫的價值從未被量過**，但它的成本已知：
每問一次 LLM、候選從 20 擴到 30–43、曾是不穩定的來源。
**建議下一輪量它**：同一批情境開／關各跑一次，比對答對率。

## 三、模型設定（本輪發現的系統性問題）

**三個 LLM 呼叫點原本各自寫死 `gpt-3.5-turbo` 作為 fallback**，
而全棧其餘走 `OPENAI_MODEL=gpt-4o-mini`：

| 呼叫點 | 原 fallback | 現況 |
|---|---|---|
| Query Rewrite | `gpt-3.5-turbo` | 已改跟隨全棧 |
| 適用性把關 | `gpt-3.5-turbo` | 已改跟隨全棧 |
| （其他呼叫點）| — | **未盤查完，值得逐一確認** |

**教訓**：`os.getenv("X_MODEL", os.getenv("LLM_MODEL", "gpt-3.5-turbo"))` 這種
兩層 fallback 會讓最弱的模型悄悄接手最吃判斷力的工作。
新增 LLM 呼叫點時，fallback 一律指向 `OPENAI_MODEL`。

## 四、量測紀律（本輪三次翻盤的代價）

離線重建 pipeline **失敗三次**，每次都讓結論作廢：

| # | 漏掉的環節 | 後果 |
|---|---|---|
| 1 | 錨點濾除（55 筆空答案列，在把關前被 `_drop_empty_answer_rows` 移除）| top-1 算錯，誤判案例分類 |
| 2 | 面向分岔（在把關**之前**截流約 30% 流量）| 直答/查無比例整組偏移 |
| 3 | Query Rewrite 擴充候選（+10–23 筆）與關鍵字備選 | 候選集約為線上的一半，三題結論相反 |

**結論：不要離線重建 pipeline。驅動真實 API。**
而且**選情境不是選樣本**——10 題按機制路徑挑，比 241 筆隨機抽樣更有用。

正確的 runner 必須完整複刻：
```
Query Rewrite → Vector top-20 → 改寫查詢聯集 → 關鍵字備選
  → Reranker → 【面向判定（用濾錨點之前的 top-1）】
       ├─ 命中且 final ≥ FORM_TRIGGER_THRESHOLD → 多輪面向（不經把關）
       └─ 未命中 ↓
  → 錨點濾除 → 適用性把關 → 表單／API／直答 → Generation
```

## 五、殘餘的不確定性

**路由仍非決定性**：改寫已完全穩定後，「如果要停用租客帳號，該怎麼做？」
5 次仍有 1 次進錯面向（改善：3/5 → 4/5）。
**來源不是改寫**（輸出已一致），疑為精排近同分時排序翻轉，**未確認**。

在路由本身仍有抖動的前提下，任何精度工作（門檻微調、selector）
都是在不穩的地基上進行。**這應優先於其他調校釐清。**
