## 一、本輪已改（分支內）

| 參數 | 舊值 | 新值 | 為什麼 |
|---|---|---|---|
| `QUERY_REWRITE_MODEL` | `gpt-3.5-turbo`（顯式設定＋程式 fallback）| **跟隨 `OPENAI_MODEL`**（現為 `gpt-4o-mini`）| 3.5-turbo 產出簡體與中國用語（租戶／请求／规定），改寫後向量偏離知識庫用詞 |

| `RELEVANCE_GATE_MODEL` | 未設 → fallback 寫死 `gpt-3.5-turbo` | **跟隨 `OPENAI_MODEL`** | 同一 prompt 換模型差 12 分（8/25 → 20/25） |

### 驗證結果（2026-08-22 複測，15 題 × 3 次，走實際配置的 rewriter）

| 指標 | 結果 |
|---|---|
| 中國用語（租戶／合同／信息…）| **0** ✅ |
| 簡體專有字 | **0** ✅ |
| 知識庫從未出現的用字 | 2 次（「補救**措**施」的措／救——正體中文，只是 KB 未用過此詞）|
| **同句 3 次改寫不一致** | **6/15（40%）** ⛔ |

**用語問題已解決**（換模型有效）。**但決定性沒有解決。**

> ⚠️ **更正**：commit `12c8a74` 訊息中「改寫已完全決定性」是**錯的**——
> 那是從 2 題觀察過度推論。擴大到 15 題後，40% 的題目改寫仍會變，

**建議修法：快取改寫結果**（同一 query → 同一改寫）。
專案已有 `cache_service`，這同時解決三件事：決定性、延遲、成本。
**尚未實作，屬待決項。**

## 二、待決參數（需要拍板或更多實證）

### `FORM_TRIGGER_THRESHOLD` = `0.75` ⚠️ 影響最大

**一顆門檻同時管兩件事**：面向進場 **與** 表單觸發（`services/decision_layer.py`
`facet_entry_eligible` / `form_trigger_eligible`）。

| 面向 | 說明 |
|---|---|
| 控制什麼 | top-1 知識 final ≥ 此值，且其 `categories` 命中啟用面向 → **進多輪對話，繞過適用性把關** |
| 實測影響面 | 約 **30%** 的 b2b 流量被面向截走 |
| 已知問題 | 0.75 實測**零攔截**（所有截流案例都遠高於它），明顯過鬆 |
| 往上抬的效果 | ⚠️ **低信心**：曲線是對 17 個錯誤案例擬合，樣本來歷未確證、單人標記一次。可用結論僅「0.75 過鬆」，**具體數字不要從該樣本挑** |
| 為何門檻不是解法 | 6 筆資訊型問題以 final **≥0.945** 進面向——任何門檻都擋不到。需要的是 routability 判定 |
| 風險 | 抬高會同時影響**表單觸發**（同一顆值），須分開評估 |

**建議**：先確認是否要把面向與表單的門檻**拆成兩個變數**，再談數值。

### `KB_SIMILARITY_THRESHOLD` = `0.65`
知識進入答題候選的門檻。本輪未量測，**不要動**。

### `RERANKER_MIN_VECTOR_SIMILARITY` = `0.3`
送進 reranker 前先砍掉向量低於此值的候選（`base_retriever`）。
實測日誌常見「下限 vector>=0.3 砍 0 筆」——目前幾乎不生效，**不要動**。

### `RERANKER_INPUT_LIMIT` = `20`
送進 reranker 的候選上限。⚠️ **注意交互作用**：query rewrite 會把候選從 20 擴到
30–43 筆，這個上限會再砍回 20——**擴充來的候選有一部分直接被丟棄**。
本輪未量測被丟棄的是不是有價值的，**值得單獨查**。

### `ADVISOR_TEMP` = `0.4`（程式預設，env 未設）
最終答案生成的溫度。**任何 e2e 對話實驗會被它污染**——
本輪實測同句 5 次答案措辭皆不同（路由相同）。
做 e2e 量測前應暫時設 0，或接受措辭變異。

### `ENABLE_QUERY_REWRITE` = `true`（全域）／ `ENABLE_QUERY_REWRITE_B2B` = `false`（本輪新增）

**已量測（2026-08-22 A/B）**：10 個機制情境 × 各 3 次，走真實 API，
`ENABLE_QUERY_REWRITE` 開/關 → **10/10 結果完全相同**。
含特地挑來測「改寫最該幫上忙」的口語模糊題（「物件建好了為什麼發佈不了啊？」）
——兩臂都給出同樣正確的三點排查。

| | 開 | 關 |
|---|---|---|
| 命中正解的情境 | 3/3 × 4 題 | 3/3 × 4 題（同知識）|
| 誠實 fallback 的情境 | 3/3 × 2 題 | 3/3 × 2 題 |
| 進面向反問的情境 | 3/3 × 3 題 | 3/3 × 3 題（同方向）|

成本卻明確：每問一次 LLM（約 600–800ms）、`temperature=0` 仍有 40% 題目
輸出不穩（路由抖動已確認來源之一）、曾產出簡體與中國用語。

**定案（業主「先只管 b2b」）**：新增 `ENABLE_QUERY_REWRITE_B2B=false`，
b2b 路徑跳過改寫；**b2c／SOP 維持啟用**。
實作於 `base_retriever.retrieve()`，b2b 判定與 `_vector_search` 同式。

> ⚠️ **b2c／SOP 未量測，不得比照關閉。**
> `REWRITE_PROMPT` 的範例（垃圾怎麼分／冷氣壞了／可以養狗嗎）
> **整個是為 b2c 租客社區問題寫的**，對 SOP 檢索可能真的有用。
> 要關 b2c 前必須先比照量過。

#### 機制（2026-08-22 補測，30 題 × 60 個改寫句）

| 指標 | 結果 |
|---|---|
| 改寫 top-1 相似度**較原句高** | **39/60** |
| 較原句低 | 21/60 |
| 改寫換掉了 top-1 | 31/60 |
| **帶進原句 top-20 沒有的知識** | **5/60（8%）** |

**改寫在相似度上是淨正的**，但**相似度高 ≠ 答案更好**。
「帶進新知識」那 5 筆多數是**把該查無的問題推向高分錯答**：

| 問 | 原句 top-1 | 改寫後 |
|---|---|---|
| 「我還在觀望，想先聽聽你們的想法」| kb3981（0.354，錯）| kb4562 想改合約租期（**0.639**，一樣錯）|
| 「你們跟 Bananas 比」| kb3981（0.281，錯）| kb3365 修繕進度（**0.432**，一樣錯）|

在 precision-first 的系統裡，這是把安全的「查無」推向自信的錯答。

**稀有的正面案例**：#18「續約後找不到帳單」原句 top-1 是錯的 kb3968（0.6050），
兩個改寫都撈到正解 kb3857（0.7299／0.6706）——**但 A/B 顯示最終答案沒差**，
reranker 與面向截流把它浪費掉了。

> ⚠️ **更正**：先前以 8 題得出「改寫相似度淨值為負（6 好 10 壞）」——
> **擴到 30 題後翻盤（39 好 21 壞），該結論作廢。**
> 關閉 b2b 改寫的依據是 **A/B 最終行為零差異＋成本明確＋提分方式有風險**，
> 不是「相似度較差」。

> ⚠️ 原推測「改寫加的候選被 `RERANKER_INPUT_LIMIT=20` 砍掉」——
> 兩臂之間重建容器導致 ON 臂日誌已失，**此路徑仍未驗證**。

## 三、模型設定（本輪發現的系統性問題）

**三個 LLM 呼叫點原本各自寫死 `gpt-3.5-turbo` 作為 fallback**，
而全棧其餘走 `OPENAI_MODEL=gpt-4o-mini`：

| 呼叫點 | 原 fallback | 現況 |
|---|---|---|
| Query Rewrite | `gpt-3.5-turbo` | 已改跟隨全棧 |
| 適用性把關 | `gpt-3.5-turbo` | 已改跟隨全棧 |
| （其他呼叫點）| — | **未盤查完，值得逐一確認** |

**教訓**：`os.getenv("X_MODEL", os.getenv("LLM_MODEL", "gpt-3.5-turbo"))` 這種
兩層 fallback 會讓最弱的模型悄悄接手最吃判斷力的工作。
新增 LLM 呼叫點時，fallback 一律指向 `OPENAI_MODEL`。

## 四、量測紀律（本輪三次翻盤的代價）

離線重建 pipeline **失敗三次**，每次都讓結論作廢：

| # | 漏掉的環節 | 後果 |
|---|---|---|
| 1 | 錨點濾除（55 筆空答案列，在把關前被 `_drop_empty_answer_rows` 移除）| top-1 算錯，誤判案例分類 |
| 2 | 面向分岔（在把關**之前**截流約 30% 流量）| 直答/查無比例整組偏移 |
| 3 | Query Rewrite 擴充候選（+10–23 筆）與關鍵字備選 | 候選集約為線上的一半，三題結論相反 |

**結論：不要離線重建 pipeline。驅動真實 API。**
而且**選情境不是選樣本**——10 題按機制路徑挑，比 241 筆隨機抽樣更有用。

### ⚠️ 樣本量紀律（本輪三次「擴大樣本就翻盤」）

| # | 小樣本結論 | 擴大後 |
|---|---|---|
| 1 | 25 筆語料可用 | 14 筆正解是事後補寫的，語料報廢 |
| 2 | 72 筆 routing 標記的 precision | 離線 runner 不忠實，整組作廢 |
| 3 | 8 題「改寫相似度淨值為負」 | 30 題後翻盤為淨正 |

**規約：任何比較性結論，起手 30 題起跳，不是 8 題。**
機制驗證可以 10 題（看路徑分岔），但**比大小一律要 30 題**。

正確的 runner 必須完整複刻：
```
Query Rewrite → Vector top-20 → 改寫查詢聯集 → 關鍵字備選
  → Reranker → 【面向判定（用濾錨點之前的 top-1）】
       ├─ 命中且 final ≥ FORM_TRIGGER_THRESHOLD → 多輪面向（不經把關）
       └─ 未命中 ↓
  → 錨點濾除 → 適用性把關 → 表單／API／直答 → Generation
```

## 六、面向進場：現況與 pre-entry routability（2026-08-23 實測）

### 現況：有進場條件，但**沒有 routability 判準**

進場只做三步，**沒有任何一步在問「這個使用者的問題適不適合這個 workflow」**：

```python
if best_knowledge['similarity'] >= FORM_TRIGGER_THRESHOLD:   # ① 分數門檻
    for cat in best_knowledge['categories']:                 # ② 讀該知識的靜態標籤
        cfg = config_for_category(cat)                       # ③ 查表
        if cfg: → 進面向
```

判的是「**這篇知識夠不夠像，而且它有沒有掛 workflow**」，
不是「**使用者現在的問題，是否真的適合進這個 workflow**」。

⚠️ 這**補標籤救不了**：標籤本身沒錯（kb「物件操作引導」掛物件操作是對的），
錯的是推論——「知識像 + 知識掛 X」⇏「這個問題該進 X 的 workflow」。

### 既有的 routability 判斷在**進場之後**

面向引擎的 brain 每輪輸出 `scope: stay|switch`，`switch` → 關會話重路由。
規則（`estate_guide` 為例）明列範疇：

> 特定物件的現況問題 → `switch` 轉物件現況診斷；合約/點交/押金操作 → `switch`（合約）；
> 成員/權限 → `switch`（帳號）…**不確定 → stay 並澄清**

**語義確實是 routability**，但校準**偏向放行**——與適用性把關改嚴前的「判定從寬」同一個病。

### ⭐ 前移在技術上幾乎零成本

`conversational_step` 的 user_prompt 六個欄位，**進場那一輪全是空的**：
`collected_fields={}`、`asked_count=0`、`recommended=False`、`grounding_note=""`、`dialog=[]`。
實際只餵了原始問句。**「前移」不是搬程式，是把同一次呼叫挪到 commit 之前。**

### Replay 實測（14 案：6 錯路由 + 8 正確路由，各 3–5 次）

| 指標 | 結果 |
|---|---|
| 整體正確 | 10/14 |
| **該擋沒擋（false accept）** | **3/6** |
| 不該擋卻擋（false reject） | **0–1/8** |

**拆算「判斷錯」vs「判斷正確但被 validator 丟棄」**（6 筆錯路由 × 5 次）：

| | 筆數 |
|---|---|
| brain **判斷正確** | 3（其中 **1** 筆被 validator 丟棄）|
| brain **判斷錯** | 3（`('ask','stay','')` 連續 5/5，**穩定錯判非噪音**）|

穩定錯判的三筆：「物件數量達到上限」→`billing_invoice`、
「我想增加一個物件」→`contract_create_guide`、「帳單發送按鈕按不了」→`billing_flow`。

### 結論：**不需要新造 selector**

既有 brain 前移即有 **50% 攔截率、幾乎零誤殺**。
要提升攔截率是改 calibration（「不確定 → **不進場**」），屬 prompt 改動，
比另造一顆判斷模型便宜一個量級。

架構問題因此重新定義為：
> 既有 Conversational Brain 已具 routability 判斷能力，但判斷發生在 commit 後。
> **能否把既有判斷安全地提前到 commit 前？**

### ⛔ 連帶發現的 validator bug（**本輪刻意不修**）

`llm_answer_optimizer.conversational_step` 驗證順序：

```python
if data.get('action') not in ('ask','converge','confirm'):
    return None                                    # ← 整包丟棄
...
data['scope'] = 'switch' if data.get('scope')=='switch' else 'stay'   # ← 永遠到不了
```

實測「停用租客帳號」→`estate_guide`：brain **5/5 正確輸出**
`scope="switch"`、`face="帳號"`，但 `action` 也被填成 `"switch"`（越界）→ **整包丟棄**。
live 表現為「引擎降級」，**設計中的改道從未執行過**。

> ⚠️ **業主定案（2026-08-23）：不修全域 validator。**
> 修它等於同時啟用兩件事——① 想要的 pre-entry 保護、
> ② 一條可能從未真正跑過的 **mid-session switch** 能力，後者 blast radius 未量。
> **pre-entry gate 應做 entry-scoped 窄修**（entry path 才讓 scope 優先於 action），
> mid-session validator 維持現狀，另開 ticket。

### 議程（業主定序）
```
A. 現況落檔、凍結量測          ← 本 commit
B. pre-entry routability gate（entry-scoped，不動全域 validator）
C. 重新量 routing precision / recall
D. 另開 ticket 查 mid-session switch bug
```
B 的兩項必要改動：①entry path 讓 `scope` 優先於 `action` 驗證；
②calibration 改為「不確定是否屬於 proposed workflow → 不進場」。
`ADVISOR_TEMP` 0.4 → 0 可一起測，但**三者要能分開歸因**，
不得混成一個不可拆的實驗。

## 五、殘餘的不確定性

**路由仍非決定性**：「如果要停用租客帳號，該怎麼做？」5 次仍有 1 次進錯面向
（改善：3/5 → 4/5）。

來源**至少有一個已確認**：改寫本身在 temp 0 仍有 40% 的題目會變（見第一節複測），
候選集因此不同。是否另有精排近同分翻轉，**尚未確認**。
→ **先做改寫快取**，消除這個已知來源，再看路由還剩多少抖動。

在路由本身仍有抖動的前提下，任何精度工作（門檻微調、selector）
都是在不穩的地基上進行。**這應優先於其他調校釐清。**
