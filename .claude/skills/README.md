# JGB AIChatbot 產線 skill 對照表

> **入口與跨線鐵律。** 放在 `.claude/skills/` 而不是 `docs/` 是刻意的：改產線時會動到
> 旁邊的 skill，順手就會維護；放 `docs/` 一陣子就過期
> （本專案已有實證：`docs/architecture/COMPLETE_CONVERSATION_ARCHITECTURE.md` §3
> 五處過濾機制描述全錯，仍被當母圖引用）。
>
> ⚠️ **這裡不寫進度數字、不寫覆蓋率、不寫筆數。** 要知道現況一律跑
> **`python3 scripts/status.py`**（開工第一件事）或 `make audit`（不變量）。寫死的數字會過期，**過期的數字比沒有數字更傷**
> ——本專案已有實證：`62.8%` 這個不存在的基準被引用了整個 session。

## 一條產線，兩把尺

```
檢索改善  retrieval-improvement-loop
          G1前提閘門 → ①收斂情境 → G2管線自證 → ③回測基準 → ④成因盤查
          → G3單一變因 → ⑤優化 → ⑥對照回測 → ⑦入庫

          兩把尺由另外兩支提供，⛔ 不在本線重寫：
            holdout-validation        判定型輸出（分類／路由／面向進場）的凍結留出紀律
            answer-acceptance-verify  自由文字回答的接受範圍（必含／禁止／允許）

設定治理  config-governance-review    ⚠️ 橫向治理，不是產線的一段
          L1 結構 → L2 一致性 → L3 語義歸屬（只提案，⛔ 絕不寫 DB）
```

⛔ **「跑完回測」≠ 跑完一輪。** 第 ⑦ 步入庫沒做完，等於沒做：

```text
① 資料改動沒產 rollback        ⇒ 出事時只能靠記憶
② 沒加稽核不變量               ⇒ 同一類 bug 會再來一次（本專案鐵則：修一類加一條）
③ 只改線上、沒改 DDL／建表腳本  ⇒ **下次重建資料庫，缺陷原封不動回來**
④ 沒標樣本已燒毀               ⇒ 下一輪拿它宣稱泛化能力
```

⚠️ **2026-09-01 實例**：一輪裡連續產生三個錯結論，全部不是分析能力問題，是順序問題
——沒讀契約就抽樣（整批做在真實流量 21 筆的通道上，另一邊有 1,321 筆）、
沒驗量測管線（向量索引在丟答案，卻被歸因成「知識寫得不好」）、
沒查前案（重新發現一次三個月前已裁決的結論）。

⚠️ **兩把尺刻意不合併**：判定型輸出比的是**類別**，自由文字比的是**命題是否成立**，
判準形狀與失敗模式都不同，合併會把判準攪混。

## 三條跨線鐵律

> 由本專案的實測事故歸納。**這裡只寫規則本身；證據與各線實例留在原地。**
> 寫新東西前先問：**這段取代了什麼？** 答案是「沒有，是新增的」就別加，去歸納。

### ① 量尺自己可能是瞎的（⚠️ 含「你量的是不是同一個系統」）

拿一把沒驗過的尺量出來的結論，**破壞力大於沒量**——因為它會長得像證據。

- 任何要當結論用的數字，必須指得出「哪一次量測、用什麼管線量到的」；指不出就寫**未量測**。
- 換尺之前，先驗新尺看得見**舊尺抓到的已知病灶**。
- 否定結論（沒有／找不到／不存在）必須含一個**已知必然存在**的正對照；
  它若也沒中，是工具壞了，不是目標不存在。
- ⛔ **「延遲沒變」「回滿了 k 筆」都不是管線健康的證據**——索引丟答案時延遲反而更低、
  回傳筆數也可能是滿的。
- ⛔ **量測一律走生產的正式入口**；要看中間狀態就用生產程式的 debug 開關，
  ⛔ 不得自寫 SQL 或重新實作過濾邏輯——那量到的是你的工具，不是系統。
- ⛔ **元件層不得用來宣稱療效**：spec 階段已測過元件，療效只在使用者看得到的那一層成立。

**各線實例**：檢索線的 IVFFlat 索引召回 31%（`ivfflat-index-defect.md`）、
舊 image 讓整輪回測翻盤、`threshold=0.0` 被 `or default` 靜默換成 0.6。

### ② 同一件事有兩個真相來源，就會靜默分岔

分岔沒有徵兆，而且兩邊都看起來正常。

- 環境值**一律 `printenv` 實查**，⛔ 不看 compose 也 ⛔ 不看程式預設——本專案三者常不一致。
- 決定被推翻或升級時，**改寫原記錄，不要另起一段**；兩段並存就會有人只讀到舊那段。
- **文件與程式衝突時一律以程式為準**，並當場把文件標記或退休，⛔ 不留「參考用」。
- 線上狀態改了，**建表／migration 原始碼要一起改**——只改線上等於埋一顆重建時引爆的雷。

**各線實例**：`ENABLE_RERANKER` 程式預設 false／compose true；
`KB_SIMILARITY_THRESHOLD` 程式 0.55／compose 硬編 0.65；三顆不同用途的「0.6 系」門檻
被文件混為一談（`b2b-doc-status-ledger.md` 錯誤熱點①）。

### ③ 先定調，再看數字

先講清楚「什麼數字會讓我選 A、什麼會讓我選 B」，**再**去查那個數字。
否則會往「反正這樣比較好做」的方向解讀，而不知道自己迴避了什麼。

- 選題規則、判準、通過門檻，一律**在抽樣與執行之前**凍結並落 sha256。
- 規則要改：新開一版、註明原因、同 seed 重抽，舊版抽樣保留可覆核。
  ⚠️ 只有在**尚未跑過任何量測**時改規則才乾淨。
- ⛔ 看過系統輸出之後不得改判準、不得補題、不得換題——那是用答案改考卷。

## 跨 skill 的共同規約

- **作者不得終審自己**：實作方自己產的判準或自評結果不是第二層驗證。
  ⚠️ **2026-09-02 業主定案已改寫執行方式**（本條原寫「一律由業主確認」）：
  「該命中哪筆」「這是不是知識缺口」**由實作方判定並逐題附可覆核證據，業主抽驗**——
  ⛔ **不是逐題核可**。防自我蓋章靠「證據可覆核 ＋ 事後抽驗 ＋ 獨立代理反證」，
  ⛔ 不是「事前逐題放行」。代價已實證：6 題全數上呈 → 來回七輪 → 零產出，
  而收手後 1 分 43 秒就自己判出 4/6 庫裡有答案。
  ⇒ 判準見 `retrieval-improvement-loop/rules/正解判定.md` §一與 `rules/該不該問業主.md`。
- **提名 ⛔ 不得使用被驗系統自己的排序**——那會讓尺與系統同構，及格線又回到被驗方手上。
- **破壞性／線上操作 ⛔ 不代跑**：給逐條指令＋預期輸出，業主自己執行；⛔ 不打包腳本。
- **每輪的實測記錄寫進 `.kiro/specs/<spec>/`，⛔ 不寫進 skill**；skill 只在**長出新規則**時才改。
  封住 skill 的成長率。
- **規則連同它的實測證據一起放**，不要為了精簡把具體清單、數字、反例拿掉
  ——抽象化過的規則，下一個人看不出它在防什麼。
