# G2 量測管線自證：跑基準之前先證明量尺沒壞

> 流程全圖、鐵律與閘門見 [`../SKILL.md`](../SKILL.md)。**⛔ 本檔只放這一塊。**
>
> 任一項紅 ⇒ **先修管線，⛔ 不准往下量**。用壞掉的管線做出來的成因分類全部作廢。

## 五項健檢

### ① 容器與 HEAD 一致
```bash
make audit        # 不變量 3 必須 PASS
```
⚠️ 舊 image 讓整輪結論翻盤——本專案 2026-08-10 已踩過一次，整輪回測作廢重跑。

### ② ANN vs 精確掃描對照 ★ 最容易被忽略、代價最大
同一批問句各跑一次，比 **top-1 是否相同**與 **top-k 候選池重疊率**。

```sql
-- 精確：關掉索引掃描
SET LOCAL enable_indexscan = off;
SET LOCAL enable_bitmapscan = off;
```

⚠️ 2026-09-01 實測：`idx_kb_embedding` 為 `ivfflat lists=100`、全表 992 筆向量、
`probes` 預設 1 且全 repo 從未設定 ⇒ **top-20 候選池平均召回率 31%、top-1 不同 46%**。
最極端一題：現行 top1 相似度 0.4568，精確掃描的正解是 **0.8308**。

⛔ **它不會報錯**：多數情況回滿了 k 筆、延遲更低，表面完全正常，只是每一筆都不對。

### ③ 門檻真的套上了
看 log 印出的閾值是不是你以為的值。

⚠️ `base_retriever.retrieve()` 寫的是 `similarity_threshold or self.default_similarity_threshold`
⇒ 傳 **`0.0` 是 falsy，會被靜默換成 0.6**。想關門檻不能傳 0。

### ④ 環境旗標實查
```bash
docker exec <container> printenv <VAR>
```
⛔ 不看 `docker-compose.*.yml`、⛔ 不看程式 `os.getenv` 預設——本專案三者常不一致：

```text
ENABLE_RERANKER            程式預設 false ／ compose true
KB_SIMILARITY_THRESHOLD    程式預設 0.55  ／ compose **硬編 0.65**（.env 蓋不掉）
ENABLE_QUERY_REWRITE_B2B   程式預設 true  ／ compose false ⇒ **b2b 不做查詢改寫**
```

### ⑤ 正對照題
批次裡放一題**已知必然命中**的。它若也沒中＝管線壞了，不是知識不足。

## ⛔ 不構成管線健康證據的東西

```text
・延遲沒變          索引丟答案時延遲反而更低
・回滿了 k 筆       候選池可能整池都是錯的
・沒有錯誤訊息      ANN 召回不足是靜默的
・上次跑過沒問題    改動可能動到管線，每輪都要重驗
```
