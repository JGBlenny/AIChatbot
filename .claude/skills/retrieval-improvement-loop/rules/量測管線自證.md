>

>

## 六項健檢

### ① 容器與 HEAD 一致
```bash
make audit        # 不變量 3 必須 PASS
```
⚠️ 舊 image 讓整輪結論翻盤——本專案 2026-08-10 已踩過一次，整輪回測作廢重跑。

### ② ANN vs 精確掃描對照 ★ 最容易被忽略、代價最大
同一批問句各跑一次，比 **top-1 是否相同**與 **top-k 候選池重疊率**。

⛔ **必須用生產程式自己的查詢**（`retrieve_knowledge_hybrid(return_unfiltered=True,
return_debug_info=True)`），⛔ **不得自寫 SQL**。
⚠️ 2026-09-01 實測：自寫 SQL 用 `ORDER BY embedding <=> v`（正規寫法、會走索引），
生產用 `ORDER BY (1 - (embedding <=> v)) DESC`（算式＋DESC、**用不到索引**）
⇒ 兩者召回率差 **70%**，而我把自寫 SQL 的結果當成了系統的行為。

```sql
-- 精確：關掉索引掃描
SET LOCAL enable_indexscan = off;
SET LOCAL enable_bitmapscan = off;
```

⚠️ 2026-09-01 實測：`idx_kb_embedding` 為 `ivfflat lists=100`、全表 992 筆向量、
`probes` 預設 1 且全 repo 從未設定 ⇒ **top-20 候選池平均召回率 31%、top-1 不同 46%**。
最極端一題：現行 top1 相似度 0.4568，精確掃描的正解是 **0.8308**。

⛔ **它不會報錯**：多數情況回滿了 k 筆、延遲更低，表面完全正常，只是每一筆都不對。

### ③ 門檻真的套上了
看 log 印出的閾值是不是你以為的值。

⚠️ `base_retriever.retrieve()` 寫的是 `similarity_threshold or self.default_similarity_threshold`
⇒ 傳 **`0.0` 是 falsy，會被靜默換成 0.6**。想關門檻不能傳 0。

### ④ 環境旗標實查
```bash
docker exec <container> printenv <VAR>
```
⛔ 不看 `docker-compose.*.yml`、⛔ 不看程式 `os.getenv` 預設——本專案三者常不一致：

```text
ENABLE_RERANKER            程式預設 false ／ compose true
KB_SIMILARITY_THRESHOLD    程式預設 0.55  ／ compose **硬編 0.65**（.env 蓋不掉）
ENABLE_QUERY_REWRITE_B2B   程式預設 true  ／ compose false ⇒ **b2b 不做查詢改寫**
```

### ⑤ Reranker **實際有沒有在跑** ★★ 2026-09-01 血證
rerank 分數佔最終合成的 **90%**（`0.1×vector + 0.9×rerank`）。它一停，
分數就落到 `max(vector, keyword) × boost` 分支，**純詞面命中直接得 1.0**，
把正解壓在下面 ⇒ 適用性閘門拿到錯的 top-1 ⇒ 判不適用 ⇒ 轉客服。

```bash
# ⛔ 不要看容器 healthy，⛔ 不要打 /api/v1/system/pipeline-health
#    那支健檢是**自己另外重新探測一次**，與正在服務請求的物件狀態無關 ⇒ 會給假綠
docker logs <app> 2>&1 | grep -E "Reranker 已啟用|SemanticReranker 服務不可用" | tail -3
docker logs <app> --since 30m 2>&1 | grep "\[Finalize\]" | tail -3
```
判讀：**最後一行**若是「⚠️ SemanticReranker 服務不可用」⇒ 現在是關的。
`[Finalize] ... rerank=0` 直接證實沒在跑。

⚠️ 成因（`semantic_reranker.py` 的 `__init__`）：建構當下打**一次** `GET /`、
`timeout=2`，失敗就 `is_available=False`，**整個 process 生命週期不再重查**。
而 semantic-model 實測延遲 >90 秒、CPU 600%+ ⇒ 2 秒探測必然失敗。
⇒ 任何一次 retriever 重建都可能把 reranker 永久關掉，**而且不會報錯**。

⛔ **這一項紅 ⇒ 本輪一切數字作廢。** 2026-09-01 實例：35 題 e2e 正好跑在失效期間，
「修前修後逐筆相同」的結論因此不可信——兩次可能都在失效態。

### ⑥ 正對照題
批次裡放一題**已知必然命中**的。它若也沒中＝管線壞了，不是知識不足。

## ⛔ 不構成管線健康證據的東西

```text
・延遲沒變          索引丟答案時延遲反而更低
・回滿了 k 筆       候選池可能整池都是錯的
・沒有錯誤訊息      ANN 召回不足是靜默的
・上次跑過沒問題    改動可能動到管線，每輪都要重驗
・容器 healthy      服務活著 ⛔ 不等於在工作；reranker 掛掉時容器仍 healthy
・健檢 API 回綠     `pipeline-health` 獨立重探測，⛔ 不反映正在服務的物件狀態
・自寫 SQL 當基準   量到的是你的工具；ORDER BY 形式一改，召回率就換一個世界
```
