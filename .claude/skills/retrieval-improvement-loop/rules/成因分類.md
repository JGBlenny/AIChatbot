# 成因七類：分錯類，優化就白做

> 流程全圖、鐵律與閘門見 [`../SKILL.md`](../SKILL.md)。**⛔ 本檔只放這一塊。**

## 七類與各自的修法

| 類 | 判準 | 修法 | ⛔ 不是 |
|---|---|---|---|
| **I 管線／索引** | 量測或檢索基礎設施本身壞了 | 修索引／參數／容器／DDL | ⛔ 不是改知識 |
| **V 可見性** | 語義最相關那筆被 `business_types`／`target_user`／`vendor_ids` 濾掉 | 改**資料歸屬** | ⛔ 不是改檢索、⛔ 不是補知識 |
| **T 門檻** | 可見，但融合分數沒過門檻 | 調門檻（⚠️ 需基準） | ⛔ 不是補知識 |
| **R 排序** | 正解有回但名次落後 | 精排／權重 | ⛔ 不是補知識 |
| **S 表示法** | 語義 top1 本身不對題 | 知識寫法／`retrieval_representation` | |
| **N 知識缺口** | 精確掃描前 15 筆全不對題 | 寫新知識 | |
| **E 進場提名** | 第①層把錯的 Face 提名上來／該提名的沒提名 | 改知識的 `categories`／面向設定 ⚠️ **或屬 governance** | ⛔ 不是改檢索、⛔ 不是補知識 |
| **G 下游否決** | 正解**可見、過門檻、且在候選列中**，卻被「檢索之後、回應之前」的某一道否決層移除或未受審即丟棄 | 改**該否決層**的參數或策略 ⚠️ **多數屬產品判斷，見下方警告** | ⛔ 不是補知識、⛔ 不是調檢索門檻、⛔ 不是改 `categories` |
| **UNCLASSIFIED** | 現有欄位不足以判定屬哪一類 | **停止並交裁決** | ⛔ 不是「先塞進最近的一類」 |

## ⚠️ E 類的特別警告（母圖 §0.2 寫死）

```text
⛔ 成功 entry ≠ responsibility 已成立
⛔ Face 有 execution capability ≠ entry 應提名該 Face
⛔ responsibility owner 存在 ≠ current entry path 一定會提出它
```

母圖 §0.3 實證 `OWNER_EXISTS_BUT_NOT_PROPOSED`：責任擁有者穩定接受（3/3 stay），
但現行提名從未提出它（9/9）。⇒ **①②之間沒有 contract bridge**。

⛔ 母圖明文：這**不是**「categories 標錯」也**不是**「某 Face priority 該調高」——
那是責任歸屬的 normative decision，屬 governance，⛔ **不得當 metadata fix 順手做掉**。
⇒ E 類要先判「是資料標註問題，還是責任歸屬問題」，後者**交裁決，⛔ 不自行修**。

## G 類的特別警告（2026-09-02 新增，⚠️ 這一類最容易被誤判成別類）

```text
已知的否決層（皆在檢索之後、回應之前，chat.py）
  _top1_relevance_gate      適用性把關。⚠️ `max_checks=2` —— **只審前兩筆**，
                            兩筆都判 NO 就回空列，**未受審的第 3–N 筆一併丟棄**
  _drop_empty_answer_rows   空答案錨點防呆
  face_precedence           面向 precedence 仲裁
```

⛔ **G 類 ⛔ 不得歸成 T 或 R**。實證（2026-09-02，35 題 b2b）：
`ts9945` top1=0.925／過門檻 5 筆、`ts7620` top1=0.951／過門檻 4 筆，兩題都轉客服。
判成 T（調門檻）或 R（調精排）對它們**在物理上不可能有效**——門檻已過、正解已在前列。

⚠️ **G 的三個子命題裁決狀態不同，⛔ 不可混計**：

```text
(a) gate 判準從「相關」改為「適用」        ✅ 已裁（2026-08-22），⛔ 不重開
(b) max_checks=2：未受審候選一律丟棄       ❓ **未裁** ⇒ ⛔ 不得援引 (a) 判為正確行為
(c) b2b fail-closed 於 LLM 失敗時清空整批  ❓ **未裁**，且必須與 (b) 分開計
```

⛔ 把 (b)(c) 算成「刻意的 precision-first 取捨 ⇒ 正確行為」會**結構性壓低失敗率**，
並把 gate 這個真正的槓桿排除在改善清單之外。⇒ (b)(c) 一律標 G ＋列入待裁清單。

## 判定順序（⛔ 不可跳）

```text
1. 先確認沒有 I —— **I 類存在時其他分類全部不可信**
2. **先看有沒有被下游否決層丟掉**（需第⑥格「否決軌跡」）
   正解在候選列中、過了門檻，卻沒被拿來回答 → **G**
   ⚠️ 第⑥格為 NOT_OBSERVABLE ⇒ **UNCLASSIFIED**，
      ⛔ 不得撈 log 補值、⛔ 不得因為「看起來像 T」就標 T
3. 再看語義 top1 對不對題
   ⚠️ **母體以第⑥格／②格實際可得者為準**：現行 ② 是 rerank 之後的 top_k（≤10）
      ⇒ S／N 的射程**僅限 top_k 之內**；top_k 之外不可觀測 ⇒ 標 NOT_OBSERVABLE，
        ⛔ 不得預設為 N（「沒看到」不等於「庫裡沒有」）
   ⚠️ 若該輪備有逐題的精確掃描前 15 筆，才可用「前 15 筆全不對題 ⇒ N」這條，
      且它**只用於對題性判定**，⛔ 其分數不得用於任何 T／R 判定（見 量測管線自證.md ②）
   不對題 → S 或 N（依上述射程）
   對題   → 再看它可不可見
              不可見 → V
              可見   → 看分數與名次 → T 或 R
4. 以上皆判不出來 → **UNCLASSIFIED**，停止並交裁決
   ⛔ 沒有 catch-all。⛔ 不得「以上皆非 ⇒ T or R」——那正是把 G 誤判成 T/R 的路徑。
```

## ⛔ 本專案已四次分錯類

```text
把 I 誤判成 S    索引丟答案 → 以為是「知識寫得不好」→ 差點去改一堆沒問題的知識
把 V 誤判成 N    知識在另一個池 → 以為庫裡沒有 → 差點去寫一篇早就存在的知識
把 G 誤判成 T/R  2026-09-02 獨立設計審查抓到：舊版本檔沒有 G 類，
                 而契約矩陣有 catch-all「以上皆非 ⇒ T or R」
                 ⇒ 門檻已過、正解已在前列的案例會被判去「調門檻／調精排」，
                   而真正的槓桿是 gate 的 max_checks。**修法方向整個相反。**
```

⇒ **每一次的修法都是白工**，而且會在錯誤的方向上累積工時與信心。

## V 類的特別警告

過濾器本身**可能是刻意的隔離機制**。動之前先查前案：

```text
docs/retrieval-recall-audit-20260822.md:82
  b2b 的 `business_types && {system_provider}` 嚴格過濾是刻意的，⛔ 勿改
```
⇒ V 類的修法是**改那筆資料的歸屬**，⛔ 不是放寬過濾器。
放寬過濾器會打穿隔離，且症狀要很久以後才看得到。
