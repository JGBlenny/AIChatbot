# 四型分批：⛔ 一批一型，混批的率讀不出意義

> 流程全圖、鐵律與閘門見 [`../SKILL.md`](../SKILL.md)。**⛔ 本檔只放這一塊。**
>
> ⚠️ **本檔 ⛔ 不寫任何筆數。** 現況一律跑 `python3 scripts/status.py`——
> 寫死的數字會腐化，而過期的數字比沒有數字更傷。

## 為什麼要分型

2026-09-01 實測：35 題**混批**跑完，得到「有引用／無引用／轉客服」三個數字，
**讀不出意義**——因為四型的「對」根本不是同一件事。

## 型別判定（機械，⛔ 不靠印象）

系統自己編碼了型別，逐筆可算：

```text
表單型   action_type='form_fill' 或 form_id 非空
T2 API   知識 action_type='api_call'
         **或** 該筆 categories 命中的面向其 grounding_scope.select='api'
T3 對話   categories 命中的面向存在，但該面向 select ≠ 'api'（純引導）
T1 直答   以上皆非
```

⚠️ 面向的型別取自「對話規則」列的 `generation_metadata.conversational_config`：
`topic_scope.mode='category'` 者才是可被 categories 提名的面向；
`grounding_scope.select` 決定它要不要查 API、`required_slots` 決定它要什麼識別碼。

## 每型的「對」完全不同

| 型 | 正解來源 | 判準 | ⛔ 禁止 |
|---|---|---|---|
| **T1 單一知識直答** | 該筆 `answer` | rubric 三欄（必含／禁止／允許） | ⛔ 逐字比對（換講法就誤殺） |
| **T2 對話＋API** | **API 回傳本身** | 逐輪：該問識別有沒有問→查到的是不是那一筆→候選列對不對→facts 逐欄比對 | ⛔ 交 LLM 判金額/狀態；⛔ 拿知識庫當正解 |
| **T3 對話引導** | 逐輪期望**動作** | 該問什麼／該收斂／該退出；⛔ 非期望字句 | ⛔ 以輪為單位報率（同 HEAD 重跑變異 13%）⇒ 以**案**為單位 |
| **表單型** | 表單契約 | 該不該觸發表單＋`field_name` 是否對齊 resolver 期望 | ⛔ 只看有沒有開表單 |

⚠️ T2 的識別碼型別（`contract_ref`／`bill_ref`／`estate_ref`／`member_ref`／`meter_ref`…）
決定了「該問什麼」——⛔ 問錯識別碼等於答錯，即使最後 facts 對了。

## 批次紀律

```text
① **一批一型**            ⛔ 不混批。混批的率無法歸因到任何一型
② **一批一類成因**        沿用 G3 單一變因；型別 × 成因交叉時先固定型別
③ 補完一批**立刻回測那一型**  ⛔ 不累積多批再一次驗——出事分不出是哪一批造成
④ 對照用**同一批凍結樣本**    ⛔ 不換題不補題（見 steps/01）
⑤ 每批的實測記錄寫進 spec    ⛔ 不寫進 skill（封住 skill 成長率）
```

## 補「categories 空」那一批的特別警告

```text
⚠️ 補 categories **是行為變更，不是純補資料**（母圖 §0.5／research 已記）
   等於把該筆知識移進一條**繞過適用性把關**的面向進場路徑
⇒ ⛔ 不得一次全掛。分批、每批補完立刻回測該型
⇒ 補完之後要看的不只是「有沒有被檢索到」，而是**有沒有錯誤地觸發面向進場**
   （＝成因分類的 E 類，見 rules/成因分類.md）
```
