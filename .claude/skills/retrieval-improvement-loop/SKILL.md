# 檢索改善迴圈

**跨線鐵律與其他產線見** [`../README.md`](../README.md)。

## 這支 skill 存在的理由

2026-09-01 實測：同一輪裡連續產生三個錯結論，**全部不是分析能力問題，是順序問題**。

```text
沒讀契約就抽樣  ⇒ 整批 19 題做在真實流量 21 筆的通道上（另一邊有 1,321 筆）
沒驗量測管線    ⇒ 向量索引在丟答案，卻被歸因成「語義召不回／知識寫得不好」
沒查前案        ⇒ 重新發現一次三個月前已裁決的結論
```

⇒ **五個步驟不值錢，三道閘門才值錢。**

## ⛔ 最上位的一條：要驗的是「完整系統 ＋ 這一刀優化」

```text
✅ 療效驗收唯一合法的層   正式入口 POST /api/v1/message（身分形狀依契約帶齊）
⚠️ 元件層                 **只能用於第 4 步成因盤查**，⛔ 不得用來宣稱療效
⛔ 自己手寫的 SQL         ⛔ 一律不得作為任何結論的依據
```

⚠️ **元件層在 spec 階段已經測過了**（單元／整合測試＋25 條稽核不變量）。
再測一次元件不會產生新資訊，只會製造「有在驗」的錯覺。
這條迴圈要買的是元件測試買不到的東西：**組起來之後使用者實際拿到什麼**。

📌 三次糾正的原文與實例見 [`rules/量測層級.md`](rules/量測層級.md)。

## 流程全圖

```text
G1 前提閘門 ─ 契約／前案／流量        ⛔ 沒寫下射程與已裁決清單，不得往下
   ↓
①  收斂情境（凍結）                   steps/01
   ↓
G2 量測管線自證 ─ **六項**健檢          ⛔ 任一項紅 ⇒ 先修管線，本輪重來
   ↓
③  回測基準 ─ **走正式入口 /api/v1/message**（⛔ 不是元件）
   ↓
④  成因盤查 ─ I／V／T／R／S／N／**E**   ⚠️ 出現 I ⇒ 回 G2
   ↓
G3 單一變因閘門                       ⛔ 一輪只動一類成因；跨類 ⇒ 拆成兩輪
   ↓
⑤  優化                               ⛔ 破壞性操作不代跑，給指令＋預期輸出
   ↓
⑥  對照回測 ─ 同樣本、同尺、**同正式入口**  ⛔ 不得換題不得補題；先重跑 G2
   ↓
⑦  入庫                               steps/07   ★ ⛔ 跑到 ⑥ 不算跑完一輪
```

⛔ **「跑完回測」≠ 跑完一輪。** ⑦ 沒做完，等於沒做：沒 rollback、沒加不變量、
沒改 DDL（下次重建資料庫缺陷回歸）、沒標樣本燒毀（下一輪拿它宣稱泛化能力）。

**自查一句：下次有人重建資料庫、或下一輪有人拿這批樣本，會不會踩到同一顆雷？**

## 三道閘門

```text
G1 前提閘門   抽任何一題之前，把「必讀清單」讀完（見下節，⛔ 不是撞到什麼讀什麼）
              出口：寫下「本輪射程」「完整流程的每一段是什麼」
                    「⛔ 已被裁決、不再討論」清單

G2 管線自證   跑基準之前先證明量尺沒壞 → rules/量測管線自證.md
              ⚡ **一行跑完**：`python3 scripts/g2_selftest.py`（任一紅則 exit 1）
                 首次使用先跑 `--self-test`（突變控制）
              出口：**六項**逐項 PASS。任一紅 ⇒ 修管線，本輪作廢重來
              ⚠️ 第⑥項（reranker 實際在跑）是 2026-09-01 用一整天換來的，
                 ⛔ 不得因為「容器 healthy」或「健檢 API 回綠」就跳過

G3 單一變因   一輪只動一類成因，**且一批只做一型**
              出口：改動逐條標明屬於哪一**類成因**與哪一**型答題面**
                    跨類或跨型 ⇒ 拆成兩輪
              ⚠️ 四型（T1 直答／T2 API／T3 對話／表單）的「對」不是同一件事，
                 混批的率無法歸因 → [`rules/型別分批.md`](rules/型別分批.md)
```

## 成因**七類**（判準與修法見 `rules/成因分類.md`）

```text
I 管線／索引   ⚠️ 這類存在時**其他分類全部不可信**，必須先清乾淨
V 可見性       改資料歸屬，⛔ 不是改檢索、⛔ 不是補知識、⛔ 不是放寬過濾器
T 門檻         調門檻（需基準）
R 排序         精排／權重
S 表示法       知識寫法／retrieval_representation
N 知識缺口     寫新知識
E 進場提名     第①層錯接／該接沒接 ⇒ 改 categories／面向設定
               ⚠️ **或屬 governance ⇒ 交裁決，⛔ 不自行修**（母圖 §0.2 三條禁止推論）
```
⛔ **七類是唯一合法的歸類詞彙**，⛔ 不得自創新名稱（README 鐵律②）。

## 第 3 步與第 6 步的兩個硬性要求

```text
③ 回測基準  **走正式入口 POST /api/v1/message** ＋ **輸出契約**（steps/03）
            跑前凍結：expected_owner／expected_kb_id（人裁兩格）
            每輪自動落：走了哪條路／候選與分數／**可見性**／面向職責／環境指紋
            ⇒ 跑完直接可歸類，⛔ 不事後撈 log 拼背景（2026-09-01 拼三次錯三次）
            ⛔ 不是 retrieve_knowledge_hybrid，⛔ 更不是自寫 SQL
            ⚠️ 非決定性：每邊 ≥3 輪取變異；成本先估並呈報
            ⚠️ **「該轉客服、也轉了」＝正確**，⛔ 不得算失敗（b2b 是 precision-first）

⑥ 對照回測  同一批凍結樣本、同一把尺、**同一個正式入口**，⛔ 不得換題不得補題
            先重跑 G2（改動可能動到管線）
            療效必須大於**同 HEAD 重跑的變異基線**（本專案 13%），否則是雜訊
            ⚠️ 改動涉及資料或 embedding ⇒ **一併重建 semantic-model**
            ⚠️ 唯一可省 e2e 的情況：元件輸出**逐筆相同**（下游輸入不變 ⇒ 輸出不會變），
              且必須明說「因為輸出相同所以省略」，⛔ 不得寫成「已驗證無療效」
```

## 驗收關卡

```text
① 三道閘門各有落檔的出口物            ⛔ 口頭通過不算
② 每題的成因分類附**可覆核的證據**    名次／分數／被哪個條件濾掉
③ 改動的預期效果事前寫下              「動哪個數字、動多少」；動不了就別做
④ ⑦ 入庫五件事全做完                  rollback／不變量／DDL／交接／燒毀標記
```

## 常見的假綠

```text
・reranker 悄悄關閉：容器 healthy、健檢 API 回綠、無錯誤訊息，但 rerank=0
  ⇒ 分數落到詞面分支，純詞面命中得 1.0 壓過正解（佔最終分數 90% 的東西不見了）
・ANN 回滿了 k 筆、延遲更低，看起來正常，但每一筆都不是對的那筆（無錯誤訊息）
・傳 threshold=0.0 想關門檻，被 `or default` 靜默換成預設值
・容器是舊 image，整輪與待測程式碼無關
・對照回測換了題或補了題 ⇒ 分母浮動，率不可比
・改了資料沒重建 semantic-model ⇒ 量到舊 surface
・不變量的判準與生產程式不同源 ⇒ 不變量綠、功能壞
・把 I 誤判成 S ⇒ 去改一堆沒問題的知識寫法
・把 V 誤判成 N ⇒ 去寫一篇庫裡早就有的知識
・拿自寫的 SQL 當系統行為 ⇒ 量到的是工具（ORDER BY 寫法不同，召回率可差 70%）
・只驗元件就宣稱療效 ⇒ 檢索回對的知識，下游仍可能把它換掉或降級成 fallback
```
