## A. 跑之前要凍結的（人裁，每題兩格）

```json
{
  "ts_id": 9885,
  "question": "這條系統訊息「以下帳單將統一於本日12:00發送」在說什麼？",
  "expected_owner": "knowledge_direct",
  "expected_kb_id": [3336],
  "why": "問的是排定發送的機制，不是查某一張帳單"
}
```

```text
expected_owner 五選一
  knowledge_direct   知識直答
  facet:<面向鍵>     該由某個面向接（⚠️ 面向鍵取自「對話規則」列，⛔ 不自創）
  api                需要 API 取現值 ⇒ **一律走 §D 判準**
                     ⚠️ **單輪 api**（一問即得、無需追問識別）只套 §D 的「輪4」與「全程」兩條，
                        ⛔ 不因為沒有輪1–3 就判失敗
  escalate           **本來就該轉客服**（⚠️ 這一格很重要：轉客服不必然是失敗）
  out_of_scope       不在本情境射程（例：b2c 題出現在 b2b 批次）
                     ⚠️ **正確行為＝誠實查無或轉客服**（⛔ 不得為它補知識、⛔ 不得放寬過濾）
                     ⇒ 它答不出來是**對的**；⛔ 也不得計入分母抬高失敗率
expected_kb_id       **陣列**：正解知識 id 一到多筆，或 ["NO_COVERAGE"]（＝真缺口，⚠️ 合法且有價值）
                     ⚠️ 需**組合多筆**才算完整回答時，全部列出（例：機制說明＋現行費率）
                     ⇒ §C 依「全中／部分中／全不中」分三態，⛔ 不得把部分中當全對
```

⛔ 提名候選 ⛔ 不得用被驗系統自己的排序（見 [`../rules/量測層級.md`](../rules/量測層級.md)）。
⛔ 標註不得由實作方單獨定案。

## B. 每輪自動落盤的（機械，⛔ 不事後撈）

```text
① 走了哪條路      usage_events：processing_path／facet_key／facet_event／answer_source
                  ⛔ **b2b 讀不到 flat 的 decision_case／knowledge_score／sop_score**
                     （2026-09-01 實查 0/261 有值）——b2b 走短路徑，
                     `_meter_comparison` 因 comparison 為 None **架構上就不呼叫**，
                     NULL 是**正確語義**，⛔ 不是資料遺漏
                  ✅ b2b 改讀 `decision_snapshot`（JSONB）：
                     `decision_snapshot->>'decision_case'`（例 `b2b_knowledge_only`）
                     `decision_snapshot->'kb_top1_final'`（＝等效 knowledge_score）
                  ⛔ `sop_score` 對 b2b **不存在等效值**——b2b 架構上完全跳過 SOP 檢索
                     ⇒ ⛔ 不得把它的缺席算成缺陷
                  ⚠️ 分母要分 mode：這三欄只有 b2c 才有機會非空
② 候選與分數      生產 debug 開關（`include_debug_info=true`）的 knowledge_candidates：
                  id／base_similarity／rerank_score／score_source／boosted_similarity／is_selected
                  ⛔ 用生產入口的 debug，⛔ 不自寫 SQL
                  ⛔ **已知缺口：面向進場路徑拿不到**——`_conversational_to_response`
                     組回應時**硬編碼不傳 `debug_info`**，不論 `include_debug_info` 為何恆 None。
                     2026-09-01 實查：`processing_path='conversational'` 佔 59/261（約 23%）
                  ⇒ 命中面向進場的題目，②這組**取不到**。當下的做法二選一：
                     (a) 該題的候選分數標 **NOT_OBSERVABLE**，⛔ 不得留空當成「沒有候選」
                     (b) 另跑一次同句、強制走知識路徑取候選（⚠️ 那是**旁路**，
                         ⛔ 不得與正式入口結果混為同一筆證據）
                  ⚠️ 這是產品缺陷，已入 `scripts/BACKLOG.md`；修好後本條可刪
③ **可見性**      對 expected_kb_id 機械算三軸過濾：
                  business_types／target_user／vendor_ids × 本輪 mode 與角色
                  ⇒ 直接標「正解存在但這個角色看不到」
                  ⚠️ 2026-09-01 實例：kb:3336 是正解，但業態不含 system_provider
                    ⇒ b2b 業者結構上看不到；**改一個欄位就好，補再多知識都沒用**
④ 面向職責        該面向「對話規則」列的 topic_scope／grounding_scope／responsibility
                  ⇒ 「該不該由它接」有客觀依據，⛔ 不靠印象
⑤ 環境指紋        printenv 實查值 ＋ reranker 實際狀態（G2⑥）
                  ⚠️ 交叉印證：debug 的 `score_source` 應為 `rerank`；
                     若為 `keyword`／`vector` 而 G2⑥ 說「已啟用」⇒ 兩者矛盾，先查再量
                  ⚠️ 含 `USE_MOCK_JGB_API`——它決定 API 型的正解是什麼
```

## C. 有了 A＋B，每題自動歸類

⚠️ 歸類詞彙**一律取自** [`../rules/成因分類.md`](../rules/成因分類.md) 的
`I／V／T／R／S／N／E` 七類，⛔ **不得自創新名稱**——
同一件事兩個真相來源就會靜默分岔（見 [`../README.md`](../README.md) 鐵律②）。

### 完整矩陣：expected_owner（5）× 實際行為（4）

| expected_owner ＼ 實際 | 直答知識 | 進面向 | 轉客服 | 走 API |
|---|---|---|---|---|
| **knowledge_direct** | 正解全中＝✅／部分中＝**R**／不對題＝**S**or**N** | **E**（不該進場卻進了） | ⚠️ **依成因分類的判定順序**：①精確掃描 top1 不對題⇒**S**（前 15 筆有正解）or **N**（都沒有）②正解不可見⇒**V** ③以上皆非、正解可見⇒**T**or**R** | **E** |
| **facet:X** | **E**（該進場卻直答） | 進 X＝✅／進 Y＝**E** | **E**（⚠️ 常見成因：適用性閘門把候選清空 ⇒ 面向失去提名） | X 是 api 型＝**續判 §D**／X 非 api 型＝**E** |
| **api** | **E** | 進對的 api 型面向＝**續判 §D**／進錯面向（含非 api 型）＝**E** | **E**or**V**（識別查無屬 §D 輪2） | 走 **§D** 判準 |
| **escalate** | ⛔ 失敗（不該答卻答了） | ⛔ 失敗 | ✅ **正確**，⛔ 不得算失敗 | ⛔ 失敗 |
| **out_of_scope** | ⛔ 失敗 | ⛔ 失敗 | ✅ **正確** | ⛔ 失敗 |

⚠️ **`escalate` 與 `out_of_scope` 兩列是「仲裁層決策」的獨立維度，⛔ 七類不適用。**
它們的 ✅／⛔ 只回答「該不該答」，⛔ 不回答「哪裡壞了」。
判為 ⛔ 失敗時，後續歸因**另循仲裁邏輯**（`services/decision_layer.py` 的
`decide_arbitration`、面向的 `responsibility` 規則），⛔ 不得硬塞進 I/V/T/R/S/N/E。

```text
⚠️ 每一格都有歸類，⛔ 不得出現「落不進任何一類」
⚠️ **E 類要再判一次**：是資料標註問題（可改 categories／面向設定），
   還是責任歸屬問題（⇒ **交裁決，⛔ 不自行修**）——見成因分類.md 的 E 類警告
⚠️ 出現 **I 管線** 類（含 reranker 沒在跑）⇒ **全表作廢**，回 G2
```

⚠️ 最後一列是今天最容易誤判的：b2b 是 precision-first，
業主已裁「接受查無比例上升，b2b 錯誤指引的成本高於一次查無」。

## D. API 型對話（T2）怎麼判對錯

> **判準是 API 回傳（grounding facts）本身，⛔ 不是知識庫、⛔ 不交 LLM 判語義。**
> 專案已裁：**formatter 決定性算 facts、LLM 只組話**。

### 逐輪判準（多輪，⛔ 不能只看最後一句）

```text
輪1  該問識別時有沒有問       ⛔ 而不是憑空答／⛔ 也不是明明能答卻索取編號
輪2  給了識別，有沒有查到**那一筆**（bill_ref／contract_id 對不對）
輪3  多筆時候選列表對不對     欄位、上限（candidate_cap）、排序
輪4  收斂後的 facts 對不對    **逐欄比對 API 回傳**
全程 回答裡每個數字／狀態      是否**逐字出現在 grounding facts 裡**
```

### ⛔ 這個判準的邊界（⚠️ 最容易被誤讀成「答對了」）

```text
本判準只保證  **忠實反映 API 回傳**（grounding fidelity）
⛔ 不保證      **API 回傳本身是對的**
⇒ 上游 API／mock 若回錯資料，系統忠實轉述會被判「對」，
  但使用者拿到的是錯資訊。
⇒ 要驗 API 資料本身，需另以合約／帳單現值對照（⚠️ 不同任務，⛔ 不在本判準射程）
⚠️ 報告首行必須寫明：本輪驗的是忠實度，不是 API 資料正確性。
```

### 分工鐵則

```text
程式比對（決定性）   金額、狀態、日期、編號、可否操作 —— 全部逐欄對 API 回傳
LLM 只判一件事       **有沒有超出 facts 亂講**（幻覺偵測）
⛔ 不用語義相似度判金額對不對
⛔ 不拿知識庫當 API 題的正解
```

### ⚠️ API 型專屬的坑

```text
USE_MOCK_JGB_API   mock **不依參數過濾、恆回固定筆數**
                   ⇒ 拿 mock 跑出來的「正確」⛔ 不等於真 API 的正確
                   ⇒ 這一格必須與環境旗標一起凍結，並在報告首行標明
金額語義           `_bill_amount_due` / `_bill_amount_received` 是不同東西
                   ⛔ 金額一律引用語義層存值，⛔ 不得重算（不變量 7）
點退／滯納金        滯納金有兩機制、違約金有 type0/1/2 —— 正解依合約現值，
                   ⛔ 不得用通則知識回答
```

## ⚠️ 凍結必須**可稽核**，⛔ 不能只是文字宣示

```text

② 回測報告首行引用**該 commit hash**
③ 稽核者一行指令即可反證：
   git log -1 --format=%cI <凍結檔>     # 凍結時間
   ⇒ 必須**早於**回測執行時間（報告需記執行起訖）
⛔ 沒有 commit hash 的凍結宣稱一律不採信。

⚠️ **這個機制的邊界（⛔ 不要誤以為它防得住偽造）**
```text
✅ 防得住   無心漏凍結、事後才想起要補標註
⛔ 防不住   **刻意偽造**——`GIT_COMMITTER_DATE=<早於執行時間>` 或
            `git commit --amend` 都能把本機 committer date 改成任意值
⇒ 本機 git log 只是**自律工具**，⛔ 不是防偽證據
若要真正不可否認：推到共享 remote，以 remote 端接收時間（reflog／CI push 記錄）為準
⚠️ 本 repo 現況 **從未 push**（見交接檔 PUB-01）⇒ 目前拿不到 remote 時間
   ⇒ 現階段只能靠自律；⛔ 報告不得宣稱「已證明凍結早於執行」，
     只能寫「本機紀錄顯示凍結早於執行」
```
