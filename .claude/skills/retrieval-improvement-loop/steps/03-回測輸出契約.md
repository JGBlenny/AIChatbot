## D. API 型對話（T2）怎麼判對錯

> **判準是 API 回傳（grounding facts）本身，⛔ 不是知識庫、⛔ 不交 LLM 判語義。**
> 專案已裁：**formatter 決定性算 facts、LLM 只組話**。

### 逐輪判準（多輪，⛔ 不能只看最後一句）

```text
輪1  該問識別時有沒有問       ⛔ 而不是憑空答／⛔ 也不是明明能答卻索取編號
輪2  給了識別，有沒有查到**那一筆**（bill_ref／contract_id 對不對）
輪3  多筆時候選列表對不對     欄位、上限（candidate_cap）、排序
輪4  收斂後的 facts 對不對    **逐欄比對 API 回傳**
全程 回答裡每個數字／狀態      是否**逐字出現在 grounding facts 裡**
```

### ⛔ 這個判準的邊界（⚠️ 最容易被誤讀成「答對了」）

```text
本判準只保證  **忠實反映 API 回傳**（grounding fidelity）
⛔ 不保證      **API 回傳本身是對的**
⇒ 上游 API／mock 若回錯資料，系統忠實轉述會被判「對」，
  但使用者拿到的是錯資訊。
⇒ 要驗 API 資料本身，需另以合約／帳單現值對照（⚠️ 不同任務，⛔ 不在本判準射程）
⚠️ 報告首行必須寫明：本輪驗的是忠實度，不是 API 資料正確性。
```

### 分工鐵則

```text
程式比對（決定性）   金額、狀態、日期、編號、可否操作 —— 全部逐欄對 API 回傳
LLM 只判一件事       **有沒有超出 facts 亂講**（幻覺偵測）
⛔ 不用語義相似度判金額對不對
⛔ 不拿知識庫當 API 題的正解
```

### ⚠️ API 型專屬的坑

```text
USE_MOCK_JGB_API   mock **不依參數過濾、恆回固定筆數**
                   ⇒ 拿 mock 跑出來的「正確」⛔ 不等於真 API 的正確
                   ⇒ 這一格必須與環境旗標一起凍結，並在報告首行標明
金額語義           `_bill_amount_due` / `_bill_amount_received` 是不同東西
                   ⛔ 金額一律引用語義層存值，⛔ 不得重算（不變量 7）
點退／滯納金        滯納金有兩機制、違約金有 type0/1/2 —— 正解依合約現值，
                   ⛔ 不得用通則知識回答
```
