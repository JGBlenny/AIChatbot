# 回答接受範圍驗證（answer acceptance verification）

## 這支 skill 存在的理由

本專案 4,875 筆 `test_scenarios` 的 `expected_answer` **全 0**，
而現行答案判定 `evaluate_answer_v2` 的及格線**硬編在被驗方自己的 repo 裡**
（`freeze_measurement` 的 docstring 自己就把這列為系統性缺陷）。
⇒ 現在跑回測，說得出「路由對不對」，說不出「答得對不對」。

補逐字標準答案不是解法：換個講法就誤殺。
**接受範圍**才是——把「對」拆成幾條可逐條打勾的命題。

⛔ 這支 skill 不判路由／分類／進場（輸出是類別的，走 `holdout-validation`）。
本支只判**自由文字回答的內容**。兩支的凍結紀律相同，⛔ 不得互相替代。

## 鐵則（違反任何一條，該輪作廢）

```text
① 代理是**對帳員**，不是裁判
   判準的每一條都必須指向一個人工指定的來源（知識 row / API 回傳 / 業主裁示）。
   ⛔ 不得出現「依常理應該…」這種由代理自身知識產生的判準。
   實證：系統曾答「待繳費不能收回」，與知識庫相反但**聽起來合理**
   ⇒ 憑常識的判官會替這種錯蓋章，而那正是最該抓的錯。

② rubric 三欄，每條都要能打勾
   ⛔ 不得寫「答得完整」「語氣專業」這類不可否證的條目。

③ 順序不可逆：寫 rubric → 人核 → 凍結(sha256) → **才**跑系統
   ⛔ 看過系統輸出之後不得改 rubric、不得補題、不得換題。

④ rubric ⛔ 不得由被驗方（實作方／我）單獨定案
   模型可草擬並機械抽候選，**業主核可才生效**。及格線必須離開被驗方。

⑤ 尺先自證：已知病灶餵進去必須紅，看不見病灶的尺其 PASS 不構成證據。

⑥ 三種情境型別 ⛔ 不得混批、不得共用一把尺（業主定案 2026-09-01）
   T1 單筆知識／T2 API 查詢／T3 對話流程——正解的**來源**不同，尺就必須不同。
   混批的後果：率被平均掉，看不出是哪一型在壞。詳見下節「情境型別」。

⑦ 判官自己的散度要量：同一份輸出重跑判官 ≥3 次
   判官散度 ≥ 系統散度 ⇒ 尺不穩，⛔ 該輪不得宣稱率。
   ⚠️ 本專案系統側參考下限：同 HEAD 重跑路由變異 13%（14/107）。
```

## 情境型別（⛔ 三型各自建集、各自報率）

```text
T1 單筆知識題 —— 一問一答，正解是庫裡既有的一段話
   正解來源  人工標註「該命中哪筆」⇒ 該 knowledge_base row 的 answer 欄位
   尺        rubric 三欄（必含事實／禁止內容／允許差異）
   判官      對帳員：逐條打勾＋原文引用
   母體      適格母體 773 中的 direct_answer 739（p0-3-knowledge-coverage-census.md）
   判定單位  單輪
   ⚠️ 這一型是唯一「標了命中就免費得到答案尺」的型別（第 1 步②）

T2 API 查詢題 —— 答案是執行期現值（帳單金額、合約狀態、繳費紀錄）
   正解來源  API 回傳本身；formatter 的決定性輸出（facts）
   尺        **決定性逐欄比對**，⛔ 不是語意相似度
             LLM 的角色僅限一條：回答有沒有**超出 facts** 亂講／自己算數字
   母體      api_call 錨點 27 筆 ＋ 走 grounding_scope.select='api' 的面向
   判定單位  單輪
   ⛔ 鐵則：機械可解碼的事實不交 LLM 判（本專案已裁：formatter 算 facts、LLM 只組話）
   ⚠️ 跑之前先確認 USE_MOCK_JGB_API 的實際值——mock 與真 API 的正解不同

T3 對話流程題 —— 多輪：進場、追問、面向切換、逃生、收斂
   正解來源  逐輪期望的**動作**（該追問什麼／該進哪個面向／該收斂／該退出），
             ⛔ 不是期望的字句
   尺        逐輪動作比對 ＋ 該輪若有作答再套 T1/T2 的尺
   母體      corpus-20260810：37 案／107 輪（25 案有業主標準答案）
   判定單位  **以案為單位**，⛔ 不以輪為單位報率
   ⚠️ 同 HEAD 重跑路由變異 13%（14/107）⇒ 單輪判定本身不穩；
      任何小於此變異的「療效」是雜訊
   ⚠️ 已知引擎級缺口會在這一型集中出現（追問不帶上下文 E-2、面向誤搶接與黏著 E-3）
      ⇒ 這一型的 FAIL ⛔ 不得直接歸因為知識覆蓋率不足
```

⛔ 三型的率**分開報**，⛔ 不得合成單一「答案正確率」——那個數字沒有可行動性。

## 執行協議

### 第 0 步：界定射程與 claim ceiling

```text
寫下  這批是 **T1 / T2 / T3 哪一型**（⛔ 一批只能一型）、母體、筆數
寫下  ⛔ 本輪不得宣稱什麼（先寫，別事後補）
      例：⛔ 不得由本輪推論線上答案品質（母體是情境集，非 production holdout）
```

### 第 1 步：取來源真相——**機械抽，⛔ 不編**

每個情境要先綁定它的真相來源，順序如下（找得到就停）：

```text
① 業主既有標準答案     docs/backtest/corpus-20260810/expected_answers.json（25 案，
                       逐字取自客服逐字稿的「標準答案」欄）
② 人工標註的命中知識   該 knowledge_base row 的 answer 欄位**就是**答案本體
                       ⇒ 只要標了「該命中哪筆」，答案尺同時到手，不必另寫
③ API 現值             api_call／面向題：formatter 的決定性輸出
④ 業主當場裁示         前三者皆無時，⛔ 必須落檔並註明是裁示不是查證
```

⛔ 沒有來源的情境**不進本批**，不要用代理生一個答案來湊。
（實證形狀：把資料直接丟 LLM 批量生成，正是 conversation-retrieval-resilience 整案還原的原因。）

### 第 2 步：草擬 rubric → 業主核 → 凍結

每案一筆，欄位固定：

```json
{
  "case_id": "01",
  "question": "<使用者原句，逐字>",
  "truth_source": {"kind": "kb_row|transcript|api|ruling", "ref": "kb:3863"},
  "must_have":  [{"id": "M1", "claim": "必須講到要先綁定金流才能發送帳單", "from": "kb:3863"}],
  "must_not":   [{"id": "N1", "claim": "⛔ 不得說待繳費帳單不能收回", "from": "kb:3335"}],
  "allowed":    ["講法與順序不拘", "詳略不拘", "加不加 CTA 不拘"],
  "verdict_rule": "must_have 全中 且 must_not 全不中 ⇒ PASS"
}
```

```text
草擬者   我（從 truth_source 機械抽候選命題，⛔ 不加自己的知識）
核可者   業主（逐案改或退；⛔ 未核可的條目不得進凍結檔）
凍結     rubric-<batch>.json ＋ sha256 落檔；⛔ 之後只能新開一版，不得就地改
`--draft-only` 停在這一步。
```

### 第 3 步：尺自證（跑系統**之前**）

```text
正控制   把已裁定的已知病灶餵給判官，**必須紅**：
         ・收據金額吐 NT$ 0（P1-a／R-31）
         ・iot_setup 搶接帳單批次題後給出與事實相反的否定（B-5）
         ・引用與新知識矛盾的舊知識 3863（F1）
         全部或任一漏抓 ⇒ 尺是瞎的，⛔ 該輪停止
突變控制 已 PASS 的輸出刪掉一條 must_have 事實 → 必須轉紅
         已 FAIL 的輸出補上該事實          → 必須轉綠
         （證明它讀的是**命題**，不是文長或表面詞）
散度     同一份輸出重跑判官 ≥3 次，記錄散度（鐵則⑦）
`--calibrate-only` 停在這一步。
```

### 第 4 步：跑系統，一次

```text
前置  ① 容器 image 與 HEAD 一致（本專案不變量 3；舊 image 會讓整輪翻盤）
      ② 確認 ENABLE_RERANKER 實際值（程式預設 false／compose true，分數管線不同）
      ③ 與換 key／改設定的時點協調——中途換會整輪作廢
輸出  回測 `replay[]` 每輪已含判官需要的四樣：
      user / answer / sources / action_type + form_id
      ⇒ 有據性與對題性**不需要任何額外標註**就判得動
```

### 第 5 步：派判官代理（隔離）

```text
給     rubric（該案那一筆）＋ 系統輸出（user / answer / sources）
⛔ 不給 知識庫全庫、系統實作、其他案的判定結果、通過門檻
規約   逐條回報，每條附**原文引用**當證據；⛔ 不得只回結論
       （尺要打得出「哪一句話讓它中／不中」，否則無法覆核）
```

判官輸出格式（**三態，⛔ 不得二分**）：

```json
{"case_id":"01",
 "must_have":[{"id":"M1","met":true,"quote":"<回答原文片段>"}],
 "must_not":[{"id":"N1","violated":false,"quote":null}],
 "verdict":"PASS|FAIL|UNJUDGEABLE",
 "unjudgeable_reason":"<缺什麼證據才能判>"}
```

```text
⚠️ UNJUDGEABLE ⛔ 不得併入 FAIL，也 ⛔ 不得併入 PASS——它是第三格，單獨報。
   （併入任一邊都會讓率失真；本專案已有三分法判讀的先例。）
```

### 第 6 步：判定與登債

```text
逐案表   case_id｜verdict｜未中的 must_have｜違反的 must_not｜判官引用
分格報   n<30 的格子只報 observed 筆數，⛔ 不報率
三態率   PASS / FAIL / UNJUDGEABLE 各自的分母都是全批
覆核     抽 ≥3 案人工覆核判官引用是否真在回答裡（防判官幻覺引用）
登債     不擋收案但要記的殘留，逐條命名
```

## 常見的假綠

```text
・判官拿常識判 JGB 專有語義（滯納金兩機制、bit_status、b2b 隔離）⇒ 替真錯蓋章
・rubric 條目寫成「應該提到相關資訊」⇒ 恆真，PASS 沒有訊息量
・逐字標準答案當 must_have ⇒ 換講法就誤殺，率被壓低成噪音
・判官引用的「原文」其實不在回答裡（幻覺引用）⇒ 第 6 步的人工覆核專治這個
・容器是舊 image ⇒ 整輪與待測程式碼無關
・把 api_call／form_fill 題丟給 LLM 判 ⇒ 判的是語氣不是事實（違反鐵則⑥）
・看過輸出後「順手把那條 must_have 講清楚一點」⇒ 用答案改考卷，整批作廢
```

## 輸出格式

```markdown
## 批次與射程
<batch 名／題型／母體／筆數>

## Claim ceiling
⛔ 本輪不得宣稱：<列表>

## rubric 凍結
路徑：<rubric-*.json>｜sha256：<...>｜核可者：業主｜核可日期：<...>

## 尺自證
正控制：<病灶> → 紅/綠（全紅才可續行）
突變控制：<改動> → 必須轉紅/綠
判官散度：<n 次重跑的散度>

## 結果
<逐案表；三態各自的率與分母；n<30 只報 observed>

## 人工覆核
<抽驗的案號與覆核結論>

## 判定
PASS / FAIL / INCONCLUSIVE（缺 <什麼證據>）

## 登債
<殘留，逐條命名>
```

## 與其他 skill 的界線

```text
holdout-validation      判**類別型**輸出（路由／分類／進場）；本支判**自由文字**
kiro-verify-completion  收案前的證據閘門；本支是它可引用的證據來源之一
config-governance-review 判設定語義歸屬；與本支無重疊
```
