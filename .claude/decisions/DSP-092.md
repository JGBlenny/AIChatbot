# DSP-092

以下為 2026-10-19 建立時的原文與依據。

**決定**：同一 session 同時只允許一張可兌現的確認卡（第 3 步 A7）。出新卡時，在 `tools/confirm.py` `confirm_request` 的同一交易內先燒掉本 session 所有未兌現 token，再 INSERT 新 token；交易開頭以 `pg_advisory_xact_lock(hashtext(session_id))` 讓同 session 的出卡排隊。燒卡沿用 `redeemed=true`。A7 屬安全強化，不隨 `AGENT_WRITE_LIFECYCLE` 開關關閉，回退＝git revert。

**業主原話**（2026-10-19）：「照建議」——回覆主會話三項建議：#9p 採 (a) advisory xact lock；#9g 修（送出後的更正不出新卡）；#9i 接受收窄。

**為什麼這樣決定**：
- 「多張卡並存」以前從未裁決過：A7 之前每張出過的卡在過期前都可兌現，舊卡可以送出過時內容（第 3 步計畫 R8「同 session 可兌現卡 ≤ 1」）。
- 計畫 §7 A7-3 原本處置「不加 advisory lock（最壞為兩張皆燒、fail-closed）」，被 2026-10-19 真 PG 實測推翻：READ COMMITTED 下兩個出卡交易交錯時，各自燒卡看不到對方未 commit 的列，結果兩張都可兌現（`tests/integration/agent/test_step3_unique_card_pg_req.py` `test_9p_interleaved_issue_leaves_at_most_one_redeemable_card` 1 failed、可兌現 2 張；正對照依序出卡 1 passed）。當時 `rag-orchestrator/services/agent` 內無任何 per-session 序列化（grep `advisory|FOR UPDATE|asyncio.Lock` 0 筆）。

**被否決的替代**：
- (b) 部分唯一索引 `session_id WHERE redeemed=false`：需新 migration；第二張卡會在唯一鍵衝突時報錯，而不是「新卡取代舊卡」，出卡路徑要另加重試。
- (c) 接受交錯風險：要收窄 R8。

**已知可用性損失（計畫 §7 A7-5，接受）**：下列情形舊卡會被燒、而新卡不成立或不是使用者要的那張：範圍閘擋下新卡（舊卡已燒、新 token 無 pending ⇒ 送出回 `confirm_unknown_pending_id`）、模型自發呼叫 `confirm.request`、文件第三道網、外部直呼 `confirm.request`。皆為 fail-closed（無法送出），不會寫錯資料。

**註記**：`routers/agent_entry.py` `handle_agent_entry` 目前無呼叫者、且用裸 `session_id`；重新掛上前須改成命名空間鍵，否則跨入口的 session 會互燒卡（計畫 §7，DEFER）。
