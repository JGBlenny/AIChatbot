# DSP-135：上線用填欄結構化 on、寫入改接與照片一起上、正式機改連 staging、照片防護關閉

**日期**：2026-10-31　**決定者**：業主

**決定**：
1. 上線用填欄結構化 on（`AGENT_FILL_STRUCTURED=on`），帶已知錯誤上線：3Q 這類道謝字進值（X9）、沒講年份的起租日被補上年份（FSB-T2）、「2萬」讀成 2（P-E2）、注入與截斷（FSB-T6、T7、FSX-bill-03）。修正輪 r1（`plan-fill-structured-r1-20261031.md`）排到上線後。不再比較 on／off 架構。依據：同批決定性題組錯筆卡 off 20、on 13（`~/jgb-archive/arch-step3-20261018/fill3/x1r/x4_stop_rootcause.md`）；off 的 OV 嚴格 75/96、M0 48/52 已在業主上線門檻 7～8 成內（`fill3/x1r/entry_close_notes.md`）。
   業主原話：「那 on 直接上線 照片報修與寫入改接 都要一起上 不要在一直做拖時間的測試」「確定 on 架構 不要在比較浪費時間了」「架構我覺得沒太大問題 不要在花時間比較了」。
2. 寫入改接（建物件、建合約、手動帳單、改到期日）與照片報修排進上線前，和 on 一起部署。計畫 `.kiro/specs/agentic-mcp-orchestration/plan-write-wiring-20261031.md`。
3. 驗收不排 OV、M0 這類整輪量測；用單元測試、每項一次 staging 實打、一次收案 verifier。業主原話：「等你絕不都測完整 這功能也根本不用上」。
4. 正式機改連 JGB staging API（`JGB_API_BASE_URL=https://staging.jgbsmart.com`），接 staging 時本系統不擋五項寫入與照片。業主原話：「阿你不會改成 staging ?」「我接 staging 也要能測到完整功能 不准檔」。已知代價：同容器的 LINE OA 一起改連 staging；staging 是 JGB 未發佈程式、資料庫是正式資料庫。2026-10-31 實測 staging 入口依來源 IP 擋正式機 `3.114.12.10`（不帶金鑰也回純文字 `Forbidden`），放行請求寫在 `jgb-spec-structured-card-draft-20261019.md` L5；切換由業主跑 `~/jgb-archive/deploy-20261031/switch-jgb-staging.sh go`。
5. 正式機關閉照片辨識的合成檔防護（`DOCUMIND_SYNTHETIC_GUARD=off`），真實照片會以明文 http 送到無認證的 DocuMind 測試機。業主 2026-10-31 自行執行 `switch-jgb-staging.sh photos-real`，即接受這個個資風險；業主並說「照片辨識的防護 為什麼要有? 感覺是一個沒用的功能」。真正的修法是 DocuMind 改 https 加認證（DSP-124 列的 DocuMind P2），防護程式保留當回退開關（`photos-guard`）。
6. 資安項只做會改變結果的（錯筆寫入、資安與個資外露、會讓上線出錯，DSP-115 第 3 點），其餘列後補。業主原話：「我今天要把完整功能上線 不必要的資安別擋住」。
7. JGB 的進度（staging 放行 IP、面板改接、合入 master）不是本系統上線的條件，也不拿來解釋本系統的進度。業主原話：「你做好你的 JGB 的問題那是他那邊的 跟你上線有什麼關係」「你一直把 jgb 的問題拿來當理由」。

**取代**：DSP-128「切換預設 on 要等 OV、M0、回歸量完並附推翻卡」（第 1 點）；DSP-124「合成檔防護維持預設開」的範圍讀法（第 5 點）；DSP-132「接真 JGB 時四個動作回固定句」由寫入改接片接手（第 2 點）。
