# DSP-131：站內幫手線就是要對齊正確架構，對話入口不排到上線後

**日期**：2026-10-30　**決定者**：業主

## 決定

- 目前的工作就是對齊 DSP-130 的目標架構。本條取代 DSP-130「上線前入口與工具都不動」「時機、順序上線後裁」。DSP-130 的目標架構本身不變。
- 對話入口先做，排在第 4 步切換正式機之前。業主原話沒有寫位置，這是主會話的讀法。
- 對話入口用加法：新增專用對話 API，重用 `_agent_turn`；`/mcp` 留到呼叫端改完才關（主會話提議，等級 C，未驗證）。
- JGB 工具照目標架構移交。JGB 要先建 MCP server，本系統不能單獨完成；排序看 JGB 能否配合，不寫成「上線後」。
- 現行文件不留讓人不去對齊的寫法。沒有使用者效果數據，不是這件事維持現況的理由。

業主原話：「換入口的好處目前沒有數據 不換也沒有好處啊」「越放只會成本越高」「就是目前本就是要對其正確架構」「我不要有誤導資訊讓你不去對其」。

架構正本放在 `docs/architecture/TARGET_ARCHITECTURE.md`（業主 2026-10-30：「你的 docs 文件也要全部更新 不是就直接 指過去 .kiro 就不管」）。`.kiro` 目標正本只寫工作線的驗收、差距細項與路徑。

## 取捨

- DSP-115 原本把不擋上線的工作往後排，對話入口不在上線最低範圍。本條是業主明示的例外，上線時間可能因此延後；延後多少未量。
- 換入口對使用者的效果沒有數據，上線當天客人看到的行為不變（逐字串流要先做逐句 Verifier）。這條的依據是系統定位與 JGB 客戶端的維護成本，不是使用者效果量測。
- 對話入口碰身分、金鑰與計量，屬資安範圍；計畫要走 `security-reviewer`、`plan-verifier` 與業主核可。本條不等於開工許可。

## 依據

方向由業主定，等級 C，沒有使用者效果數據。反向攻擊 `~/jgb-archive/arch-step3-20261018/arch-review-20261030/attack-entry-early.md` 建議維持現況；主會話依全域「推翻現況的建議」第 2 條不標推薦，方向照業主裁定。

- 本系統這邊的切換成本幾乎沒長：綁傳輸層的測試與 scripts 檔 2026-09-12 3、10-01 3、10-15 3、10-30 4。引用 `mcp_facade` 模組的檔增加較多，那是 Python 模組耦合，加法方案不用改。
- 長的是 JGB 那邊：`AgentTurnClient` 2026-10-15 版 755 行（`c0e33721c2`），staging `8ff2f7b8e7`（2026-10-30）1033 行，含 10-29 加的上傳票；master `eeccdfd8eb`（2026-10-30）沒有這支。JGB 目前接 staging 分支（業主 2026-10-30）。約 490 行屬協定層，是攻擊者的分類上界。趁還沒進 master 就換，正式站只上一種客戶端；進了 master 再換，JGB 多上版一次（主會話推論，等級 C）。
- 這支 client 每回合走 `initialize`、`notifications/initialized`、`tools/call`、`DELETE`。本機量 30 次，握手三步合計中位 33.1 ms、p95 571.7 ms（`handshake-20261030/result.txt`，同目錄），不含跨網路。延遲不是換入口的理由。MCP 2026-07-28 版移除 session 與 initialize。
- 開片前提：JGB 這支 client 哪個 release 進 master；line-bot、LIFF 的客戶端能不能換；`mcp==2.1.1` 的協定版本。
- 主要風險：兩個入口長期並存，量測全來自 `/mcp`，產品卻走新路由；入口計畫要讓新入口也有量測。
